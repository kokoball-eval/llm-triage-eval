# v1.5 확신도 기반 라우팅 계획 (사전 등록) — 7단계: 개발용 기준선

> 이 문서와 `routing_v15.toml`, `src/triage_eval/pipeline/routing.py`는 개발용 기록으로 후보를 재기 전에 커밋한다(2026-11-16). 결과를 본 뒤 규칙을 바꾸지 않는다. 바꿔야 할 이유가 생기면 다음 계획으로 넘기고 그 사실을 기록한다.

## 요약

모델이 판정한 응답마다 "사람이 한 번 더 봐야 하는 건"을 시스템이 골라 검토 큐로 보내고, 나머지는 자동 등록하는 규칙(라우터)을 만든다. 이 단계(7단계)는 이미 저장된 실행 기록으로 신호를 하나씩 더해 가며 어느 신호 집합이 쓸 만한지 고른다. **모델을 새로 돌리지 않고, 채택 판정도 하지 않는다.** 채택은 새로 봉인할 최종 평가용 세트(8단계)에서 한 번 실행해 판정한다(9단계).

## 1. 왜 하는가

최종 목표는 사람이 보지 않아도 1차 트리아지가 돌아가는 파이프라인이다. 다만 7B 로컬 모델은 모든 리포트를 맞힐 수 없으므로, 확신할 수 있는 건은 자동 등록하고 확신할 수 없는 건은 검토 큐로 보내야 한다. 성패는 두 숫자로 갈린다. 검토 없이 자동 등록된 응답 중 **위험 건 누락**(Critical을 놓침 등)과 **날조**가 0건인가, 그러면서 자동으로 처리되는 비율이 얼마나 되는가.

두 가지 사실이 설계를 정한다.

- **모델이 확신도를 출력하지 않는다.** 출력 8칸에 확신도가 없다. 형식을 바꾸면 "한 번에 하나만 바꾼다" 원칙이 깨지고, 7B 모델이 스스로 말한 확신도를 믿을 근거도 없다. 그래서 응답·입력·같은 문항의 다른 응답에서 얻는 신호를 확신도 대신 쓴다.
- **두 LLM 채점관은 모두 미채택이었다**([날조](judge_v15_results.md), [요약 품질](quality_v15_results.md)). 라우팅 신호로 쓰지 않는다.

## 2. 단위와 용어

- **응답 1건**이 라우팅 단위다. 검토 큐로 보내거나 자동 등록한다.
- **위험 누락**은 `score.py`의 X-1(Critical 문항인데 긴급 사인 요청이 아님)·X-2(결함을 폐기)·X-3(사람 확인이 필요한 문항을 사람 확인 없이 끝냄)이다. 정의는 바꾸지 않는다.
- **날조**는 `detect_hallucination.detect()`가 입력에 없는 구체 사실을 잡은 응답이다. S4가 같은 탐지기를 쓰므로, **S4가 들어간 신호 집합에서 날조 통과는 정의상 0이다.** 이 지표로는 날조 0건을 증명할 수 없다(§8).
- **위험·날조 통과**는 검토 없이 자동 등록된 응답 중 위험 누락이거나 날조인 응답이다(둘 다이면 한 건으로 센다).
- **자동 처리분 정확도**는 자동 등록된 응답 중 우선순위·모듈·처리가 모두 정답 허용 답 안인 응답의 비율이다.

## 3. 신호 (정답 라벨을 보지 않는다)

| 신호 | 검토 큐로 보내는 조건 | 비용 |
| :--- | :--- | :--- |
| S1 판정값 | 최종 응답(안전장치 적용 뒤)의 처리가 긴급 사인 요청·정보 요청 후 보류이거나 우선순위가 Critical·판단보류 | 없음 |
| S2 파이프라인 흔적 | 형식 재요청, 안전장치 적용, Critical 상향, 폐기 보류, 형식 위반, 출력 잘림, 실행 실패 중 하나 | 없음(이미 기록됨) |
| S4 날조 탐지기 | v1.2 규칙 기반 탐지기가 날조로 본 응답 | 낮음 |
| S3 반복 불일치 | 같은 문항 응답 6개(seed 3개 × 2회)의 (우선순위, 처리) 조합이 하나라도 다르면 그 문항의 모든 응답 | 높음(운영에서 같은 리포트를 여러 번 돌려야 함) |

실제 운영에서는 정답을 모르므로 신호는 정답 라벨을 보지 않는다. 라벨을 바꿔도 신호가 같음을 테스트로 확인한다.

- **실행에 실패한 응답**은 S2로 검토 큐에 가고, S3에서는 (우선순위, 처리)가 (없음, 없음)인 값으로 센다(다른 응답과 다르면 그 문항은 불일치).
- **S1은 구조상 위험 누락을 많이 잡지 못할 수 있다(결과와 무관한 사실).** 위험 누락(X-1~X-3)은 "처리가 긴급 사인 요청이 아니거나, 사람 확인 없이 끝나는 처리를 골랐다"는 뜻인데, S1은 처리가 긴급 사인 요청·정보 요청 후 보류인 응답을 검토로 보낸다. X-1 누락은 S1이 잡지 못하는 처리(개발 배정·CS 응대·폐기·등록)에서 나오므로, S1이 이미 안전한 응답을 주로 검토로 보내고 위험 응답은 놓친다면 구조상 예상된 결과다. 그 경우 위험 누락을 줄이는 일은 S2·S3의 몫이 된다.

## 4. 후보 (신호를 하나씩 더해 본다)

신호는 비용이 낮은 순서 **S1 → S2 → S4 → S3**로, **지금 선택한 신호 집합에 하나씩** 더해 본다. 한 번에 여러 신호를 더하면 무엇이 위험 누락을 줄였는지 알 수 없고, 거절한 신호가 다음 후보에 섞여 들어가면 선택 규칙이 모호해진다.

| 구성 | 신호 |
| :--- | :--- |
| R0 | 없음 — 전부 자동 등록 (비교용 기준선) |
| R1 | S1 (선택의 출발점) |
| +S2 | 지금 선택한 집합 + S2를 더해 비교 |
| +S4 | 그 결과(S2 채택·거절 반영) + S4를 더해 비교 |
| +S3 | 그 결과 + S3를 더해 비교 |

예를 들어 S2를 거절하면 다음 후보는 S1+S4이고, S2를 채택하면 S1+S2+S4다. 신호 하나만 썼을 때의 효과는 기록으로 따로 남긴다.

## 5. 입력과 지표

- **입력:** 채택 구성(qwen2.5:7b + M2)의 기준선 실행 기록 3개(`data/results/v14/baseline/`, seed 1·11·21 × 개발용 63문항 × 2회 = 378응답)를 v1.5 정답표(`data/eval_v15/`)로 채점한다. 게이트 v1.5와 같은 입력·정답표 확인(문항 ID·입력·평가셋 지문)을 거친다. 모델은 호출하지 않는다.
- **지표(후보마다):** 자동 처리율, 위험 X-1·X-2·X-3 통과 수, 날조 통과 수, 위험·날조 통과 응답 수와 그런 응답이 있는 문항 수, 자동 처리분 정확도, 검토 큐 적중률(검토 큐 응답 중 위험·날조이거나 세 칸 중 하나가 틀린 비율).
- **기록(판정에 쓰지 않음):** 신호 하나만 썼을 때 위험·날조 응답을 검토로 보내는 수, 선택한 후보에서 자동 등록된 위험·날조 응답 목록.

## 6. 신호 집합 선택 규칙 (사전 등록)

R1에서 시작해 S2, S4, S3 순서로 각 신호를 **지금 선택한 집합에 더한 집합**을 지금 선택과 비교한다. 아래 순서로 판단한다.

1. 더한 집합의 자동 처리율이 **하한 30%** 미만이면 바꾸지 않는다.
2. 위험·날조 통과 응답 수가 줄면 바꾼다.
3. 같으면서 자동 처리분 정확도가 **2.0%p 이상** 오르면 바꾼다.
4. 그 밖에는 바꾸지 않는다.

- 기준값과 같으면 충족으로 본다. 비율은 반올림하기 전의 정수 비율로 비교한다(반올림한 값을 빼면 62.1% → 64.1% 같은 정확히 2.0%p 차이가 부동소수 오차로 거절된다).
- 마지막까지 바꾸고 남은 집합이 개발용 선택 결과다. 거절한 뒤에도 남은 신호를 계속 본다.
- **규칙 2는 위험·날조 통과를 한 건만 줄여도 자동 처리율을 하한(30%)에 가깝게 낮추는 집합을 채택한다.** 위험 건 누락 0건이 목표이므로 안전 쪽으로 기운 맞바꿈을 의도했고, 결과를 본 뒤 이 맞바꿈을 고치지 않는다. 처리율 손실의 크기는 보고서의 표에 그대로 보인다.
- **S1만으로도 자동 처리율이 하한 미만이면** 선택은 S1로 기록하고(선택 없음이 아니다), 더 무거운 신호는 보지 않는다. 이 경우 9단계의 자동 처리율 목표는 이 사실을 반영해 정한다.

하한 30%와 정확도 향상 2.0%p는 근거 없이 정한 안전장치 값이다. 자동 처리율 하한은 "거의 모두를 검토로 보내 위험을 0으로 만드는" 자명한 해를 막고, 정확도 향상 기준은 우연한 차이로 집합이 바뀌는 것을 막기 위해 두었다. 어느 값도 개발용 결과를 보고 정하지 않았다.

## 7. 이 단계가 하지 않는 것

- **채택 판정.** 개발용 문항은 프롬프트를 다듬는 데 쓴 문항이라 위험 누락이 개발용 1/66, 나머지 문항 16/54였던 것([KL-003](../docs/issue_log.md#kl-003))처럼 성적이 낙관적이다. 이 결과는 후보를 고르는 데만 쓴다.
- **모델 호출, 출력 형식·프롬프트·안전장치 변경.**
- **임계값 조정.** 규칙과 임계값은 이 문서에서 고정한다.

## 8. 한계

- **개발용 문항이다.** 결과가 낙관적일 수 있고, 새 문항에서 신호의 포착력이 낮아질 수 있다.
- **응답 단위 평가다.** 같은 문항의 응답 6개는 서로 독립이 아니다. 그래서 위험·날조 통과가 있는 문항 수를 함께 남긴다.
- **S3은 운영 비용이 크다.** 같은 리포트를 여러 번 돌려야 하고, 이번 측정은 seed 3개 × 2회라는 저장된 조건을 쓴다. 한 번만 돌리는 운영과는 다르다.
- **한 모델·한 도메인이다.** qwen2.5:7b와 게임 버그 리포트만 검증한다.
- **날조 통과 지표는 S4와 같은 탐지기로 센다.** S4가 들어간 집합에서는 정의상 0이라 이 지표로 날조 0건을 증명할 수 없고, 탐지기는 규칙 기반이라 놓치는 날조가 있다(날조 측정에서 심은 날조 20건 중 1건만 잡았다). 그래서 **9단계의 날조 판정은 탐지기와 독립된 수단(새 세트 응답의 사람 확인)으로 한다.**
- **정답표 자체의 한계.** 라벨 일치율 측정에서 두 외부 채점자도 갈린 칸이 있었다([결과 보고서](label_agreement_v15_results.md) §7). 처리 칸의 허용 답은 넓게 잡혀 있다.

## 9. 진행 순서

| 순서 | 할 일 | 산출물 |
| :---: | :--- | :--- |
| 1 | 계획·기준·측정 도구·테스트 커밋 (이 문서). 측정 도구는 이 문서·기준·도구·테스트와 채점 코드(`score.py`·탐지기·`contract.py`·`prompt.py`)가 커밋되어 변경이 없을 때만 실행된다 | 이 문서, `routing_v15.toml`, `routing.py`, `tests/test_routing_v15.py` |
| 2 | 개발용 기준선 측정 1회, 후보 선택 (모델 호출 없음) | `data/results/v15/routing/routing_dev_v15.json`, `report/routing_dev_v15.md` |
| 3 | 결과 보고서와 9단계 판정 기준 확정 (새 세트를 만들기 전) | `report/routing_v15_results.md` |
| 4 | (8단계) 새 v1.5 최종 평가용 세트 봉인 | 새 평가셋 |
| 5 | (9단계) 선택한 라우터를 새 세트에서 한 번 적용, 목표 판정 | 최종 결과 보고서 |

최종 목표는 위험 건 누락 0건, 날조 0건이다. 자동 처리율과 자동 처리분 정확도의 목표는 2번의 기준선을 본 뒤 3번에서, 새 세트를 만들기 전에 정한다.

## 10. 설계 기준

| 출처 | 적용한 곳 |
| :--- | :--- |
| 게임 개발 QA 실무 | 심각도 높은 건과 정보가 부족한 건은 사람이 먼저 보는 BTS 등록 관행을 S1로 옮김. 형식 재요청·안전장치처럼 "파이프라인이 손댄 응답은 한 번 더 본다"는 점검 습관을 S2로 옮김. 같은 이슈를 여러 QA가 달리 판정하면 경계 사례로 보는 관행을 S3으로 옮김 |
| KANT AI 부트캠프 Private LLM 트랙 | 후보를 비용이 낮은 순서로 하나씩 더해 효과를 분리, 선택 규칙·임계값을 결과 전에 고정, 개발용과 최종 평가용 분리(채택은 새 세트에서), 모델 자기 보고 확신도를 쓰지 않고 외부 신호로 대체 |
| 앞선 측정에서 얻은 교훈 | 두 LLM 채점관 미채택(§1), 개발용 낙관성(KL-003, §7), 결과 선저장(ISSUE-014), 정답표 일치율 한계(§8) |
