# v1.5 9단계 계획 — 봉인된 새 최종 평가용 세트에서 라우팅 한 번 판정 (사전 등록)

> 이 문서는 모델을 실행하기 전에 커밋한다. 실행·채점·판정 결과를 본 뒤에는 이 문서와 `final_run_v15.toml`, 도구를 고치지 않는다. 바꿔야 할 이유가 생기면 다음 버전의 계획으로 넘기고 그 사실을 `docs/issue_log.md`에 남긴다.

## 1. 질문과 범위

- **질문:** 채택 구성(qwen2.5:7b + 방법 M2)이 봉인된 새 60문항에서 낸 응답에 라우터 **S1+S2**를 적용하면, 위험(X-1·X-2·X-3)·날조 응답이 검토 없이 자동 등록되는 일을 충분히 막는가?
- **바꾸는 것은 평가셋 하나뿐이다.** 모델, 프롬프트 v2.3, 형식 재요청, 방법 M2, 폐기 점검, 안전장치 g2, 신호 정의(S1·S2)는 7단계 개발용 기준선과 같다. 신호 집합은 개발용 결과로 고른 S1+S2로 고정하고 새 세트에서 다시 고르지 않는다.
- **평가셋:** `data/eval_v15_final/aether_raid_v15_final.json` (60문항, 봉인 기록 `sealed_v15.json`). 실행 전에 `seal_final_v15.verify()`가 통과해야 한다. 이 세트는 한 번 실행하면 다시 평가용으로 쓰지 않는다.
- **판정 기준:** [`routing_v15_results.md`](routing_v15_results.md) §6을 그대로 쓴다. 값은 `final_run_v15.toml`에 옮겨 적었다(§4).

## 2. 실행 규약

| 항목 | 값 | 이유 |
| :--- | :--- | :--- |
| 모델·방법 | qwen2.5:7b, M2 | 채택 구성 |
| 실행 | seed 1·11·21 × 각 2회 = 문항당 6응답, 총 360응답 | 개발용 기준선과 같은 절차라 처리율과 통과 비율을 같은 자로 비교한다 |
| 실행 명령 | `uv run triage-final run` (내부에서 `triage-run`을 `--dataset v15final --split final --final --method m2 --strict-env`로 seed마다 호출) | 기존 실행 도구의 동작은 바꾸지 않고 평가셋 선택지 하나만 더했다 |
| 환경 | 측정 환경 점검 경고가 있으면 실행하지 않는다(`--strict-env`) | 실행 중 모델 재로드 등으로 오염된 실행은 판정하지 않는다(OBS-005) |

**한 번만 쓰는 장치**

1. **STARTED 마커:** 첫 실행을 시작할 때 `data/results/v15_final/measure_started_v15_final.json`을 만들고 seed별 상태(시작·완료·기록 파일)를 적는다. 완료된 seed는 다시 실행하지 않는다.
2. **guard:** 계획·기준·도구·채점 코드·봉인 기록이 커밋되어 있고 변경이 없을 때만 실행·판정한다.
3. **봉인 확인:** 평가셋과 승인 기록의 SHA-256·문항 수·`sealed`·`approved` 상태가 봉인 기록과 같아야 한다(`triage-final`이 직접 확인한다. 봉인 도구의 `verify()`는 CI의 정합성 시험이 매번 확인한다). 실행 전에 설치된 모델의 digest가 개발용 기준선과 같은지도 확인한다(모델 호출 아님). 다르면 실행하지 않는다.
4. **재실행 규칙:** 환경 오염이나 도구 오류로 한 seed의 실행이 기록 파일을 남기기 전에 멈춘 경우에 한해, 그 seed만 `--redo-incomplete <seed>`로 다시 실행할 수 있고 마커에 기록한다. 기록 파일이 있는 seed(그 seed 시작 뒤 history에 생긴 파일이 있으면 도구가 거부한다), 또는 날조 확인·라우팅·채점 결과를 한 번이라도 본 뒤에는 다시 실행하지 않는다. 마커가 없는데 기록 폴더에 실행 기록이 있으면 마커를 지운 것으로 보고 실행하지 않는다.
5. **구성 동일성:** 판정 도구는 새 실행 기록의 구성(옵션, 프롬프트 버전·해시, 안전장치·재시도·폐기 점검 정책, 방법 자산 해시, 모델 digest)이 개발용 기준선과 같은지 확인한다. 하나라도 다르면 "구성 불일치"로 기록하고 판정하지 않는다. 기록의 평가셋 해시·문항 목록·seed 목록이 계획과 같고 세 기록 파일이 서로 다른지도 확인한다.

## 3. 순서와 눈가림

| 순서 | 할 일 | 이 단계에서 보지 않는 것 |
| :---: | :--- | :--- |
| 1 | 이 계획·기준·도구·시험을 커밋하고 CI가 초록색인지 확인한다 | — |
| 2 | `uv run triage-final run`으로 360응답을 실행한다 | 채점·라우팅·날조 결과는 계산하지 않는다 |
| 3 | **날조 사람 확인** (경민 1명, 브라우저 화면) | 정답 라벨, 라우터 신호, 점수, 탐지기 결과, 다른 칸(우선순위·처리 등)은 화면에 띄우지 않는다 |
| 4 | 확인 결과 파일 `data/final_v15/fabrication_check_v15_final.json`을 커밋한다 | 커밋 뒤에는 고치지 않는다 |
| 5 | `uv run triage-final verdict`로 라우팅·채점을 계산하고 §4 순서로 판정한다(기계 생성 표 `report/final_run_v15_measure.md`, 결과 `data/results/v15_final/routing_final_v15.json`) | 확인 결과 파일이 커밋돼 있지 않으면 판정하지 않는다 |
| 6 | 결과 보고서(`report/final_run_v15_results.md`)를 쓰고 독립 검토 후 커밋한다 | — |

**날조 확인 절차**

- **왜 라우팅 계산보다 먼저 하나:** 7단계 날조 통과는 S4(탐지기)와 같은 규칙이라 정의상 0이다. 사람이 라우팅 결과를 본 뒤에 판정하면 라우터가 잡은 응답을 날조로 더 쉽게 볼 수 있다. 확인을 먼저 끝내고 잠근다.
- **날조의 정의:** 요약에 리포트 원문(게시판·게시 일시·제목·본문·업데이트 공지·기존 등록 이슈)에 없거나 원문과 어긋나는 사실 진술이 하나라도 있으면 날조 있음이다. 원문을 다른 말로 바꿔 쓰거나 줄인 것은 날조가 아니다([`judge_v15_plan.md`](judge_v15_plan.md) §2와 같은 문구).
- **화면:** 입력 원문과 응답의 `[요약]`(요약이 여러 줄이면 다음 필드 라벨 전까지 이어 붙인 전체)만 보여 주고 "날조 있음 / 없음"을 고른다. 판단이 어려우면 메모를 남기고 하나를 고른다. 같은 문항에서 요약 문장이 글자까지 같은 응답은 한 장으로 묶어 한 번만 판정하고 묶인 응답 전체에 적용한다. 순서는 응답 식별자의 해시로 섞어 문항·seed 순서에서 오는 단서를 줄인다.
- **인원:** 경민 1명. 정답 라벨을 승인한 사람과 같다는 한계를 보고서에 적는다.
- **범위:** 360응답 전부(묶음은 한 번 판정). 실행 실패 응답은 요약이 없어 날조 없음으로 센다.

## 4. 판정 (기준은 `routing_v15_results.md` §6 그대로)

판정 단위는 응답 1건이고 문항 단위도 함께 보고한다. "위험·날조 응답"은 위험 누락(X-1·X-2·X-3)이거나 사람 확인에서 날조인 응답이다(둘 다이면 한 건). "통과"는 S1+S2 어느 쪽도 걸리지 않아 검토 없이 자동 등록된 것이다. 위험 누락은 `score.score_one`을 그대로 쓰고(게이트·재채점과 같은 자), 날조만 사람 확인 결과로 바꾼다.

**판정 순서** (위에서부터 처음 해당하는 것으로 정한다)

1. 위험·날조 응답이 **10건 미만이거나 서로 다른 문항 5개 미만**이면 **표본 부족**으로 기록하고 판정하지 않는다.
2. 자동 처리율이 **30% 미만**이면 **미채택**.
3. 위험·날조 통과가 **0건**이면 **채택**.
4. 위험·날조 응답 중 통과한 비율이 **50% 이하**이면 **부분 채택**(검토 큐를 먼저 보는 순서를 정하는 보조 도구로만 쓴다).
5. 그 밖에는 **미채택**.

비율은 반올림 전 정수 비율(Fraction)로 비교한다. 위 값 중 50%만 개발용 결과를 본 뒤에 정한 값이고 나머지는 계획 시점의 값이다. **정확도, S3, 개별 신호 효과는 판정 조건이 아니라 보고만 한다.**

**함께 보고하는 것:** 자동 처리율, 위험(X-1·X-2·X-3)별·날조 통과 건수, 위험·날조 응답과 통과 응답이 있는 문항 수, 자동 처리분 정확도, 신호 하나만 쓴 경우의 검토 응답 수, 개발용 기준선과의 비교, 날조 확인 결과(응답·묶음 수), 탐지기(S4)와 사람 판정의 일치(참고).

## 5. 미리 적는 예상

개발용 결과에서 S1+S2의 위험·날조 통과는 68.2%(22건 중 15건)였다. 새 세트에서도 비슷하다면 판정은 **미채택**이다. 그 경우 결과를 고치지 않고 신호 개선(예: 입력 문구 기반 신호)을 v1.6 후보로 넘긴다. 위험 문항을 30개 넣었으므로 표본 부족은 생기기 어렵지만, 생기면 그대로 기록한다.

## 6. 한계

- 문항을 Claude가 썼고 정답 라벨은 같은 검토자가 승인했다. 외부 QA 판정이 아니므로 라벨 오류 가능성이 남는다(1단계 일치율 미달과 같은 한계).
- 날조 확인도 한 사람이 한다. 단, 라우팅·정답을 가린 상태에서 먼저 확정하고 커밋한다.
- 위험 문항 비율을 높였으므로 이 세트의 통과 비율은 실제 인입 분포를 대표하지 않는다.
- 모델 하나, 방법 하나, 구성 하나만 잰다. 다른 모델에는 일반화하지 않는다.
- 같은 문항의 6응답은 서로 독립이 아니다. 응답 수와 문항 수를 함께 보고한다.
- NA16·NA18·NB11의 정답은 기준서 v1.5와 다른 검토자 판단을 따른다(V16-2).

## 8. 하지 않는 것

- 신호 집합 재선택, 임계값 조정, 새 신호 추가.
- 이 세트로 프롬프트·방법을 고치는 일. 이 세트의 응답을 보고 개발용 문항을 바꾸는 일.
- 결과를 본 뒤 재실행. 이 세트의 재사용.

## 9. QA 실무 경험과 부트캠프 학습의 활용

- **QA 경험:** 릴리스 직전 빌드에서 어떤 건은 자동 통과시키고 어떤 건은 사람이 다시 보는 검수 선별 문제와 같은 구조다. 개발 중에 정한 선별 규칙을 검증하지 않은 새 빌드에서 한 번만 시험한다. 결함이 있는 응답을 "검토 큐로 보낸 비율"이 아니라 "놓친 건 수"로 세는 것도 QA의 누락(escape) 집계와 같다.
- **부트캠프(Private LLM 트랙):** 평가 데이터 누수 방지(봉인·해시·한 번만 실행하는 STARTED 마커), 사전 등록 판정, 라우팅 결과를 가린 상태에서 먼저 확정하는 사람 평가, LLM 탐지기와 독립된 사람 판정을 적용했다.
