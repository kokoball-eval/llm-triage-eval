# v1.4 실행 기록 v1.5 라벨 재채점 계획 (사전 등록)

> **상태: 재채점 결과를 보기 전에 확정 (2026-10-15).** 이 문서는 재채점 도구를 실제 실행 기록에 돌리기 전에 커밋한다. 결과를 본 뒤에는 대상·지표·검증 기준·해석 규칙을 바꾸지 않는다. 바꿔야 할 이유가 생기면 다음 버전 계획으로 넘기고 그 사실을 기록한다.

## 요약

- **질문** — v1.4에서 잰 채택 구성(qwen2.5:7b + M2)의 정답률과 Critical 누락은 v1.5 라벨로 채점해도 같은 그림인가? 라벨이 바뀌면서 v1.4의 방법·모델 채택 판정이 흔들리는가?
- **방법** — 저장된 v1.4 실행 기록을 **모델을 다시 호출하지 않고** v1.4 라벨과 v1.5 라벨로 각각 채점해 나란히 놓는다. 모델 응답은 그대로이고 정답표만 바뀌므로, 숫자 차이는 모두 라벨 변경에서 나온다.
- **쓰임** — v1.5 이후 단계(게이트 기준선 재작성, LLM-as-judge, 라우팅)가 v1.5 라벨 기준의 출발점을 알 수 있게 한다. 사전 등록 판정(M2 채택, 게이트 PASS)은 바꾸지 않는다.

## 1. 왜 재는가

v1.5 라벨 일치율 검토(`report/label_agreement_v15.md`, `docs/dataset/review_log.md`)에서 개발용 33문항 53칸의 허용 답이 바뀌었다. 그중 위험 표시도 바뀌어 Critical 측정 문항이 20건에서 17건이 되었다(B17 추가, S04·S08·S09 등 제외). 같은 모델 응답이라도 정답표가 바뀌면 정답률과 Critical 누락 수가 달라진다.

QA 실무로 보면, 심각도 기준표를 개정한 뒤 **지난 테스트 회차의 판정 결과를 새 기준표로 다시 집계하는 작업**이다. 버그를 다시 재현하지 않고 판정 기준만 바꿔 다시 세므로, 숫자 차이가 "제품이 달라져서"가 아니라 "자가 달라져서" 생긴 것임이 분명하다. 부트캠프 Private LLM 트랙에서 다룬 평가 원칙(평가 데이터·채점 기준을 고정하고 한 번에 하나만 바꾼다)을 그대로 적용한다. 이번에 바꾸는 것은 라벨 하나뿐이다.

## 2. 대상

| 대상 | 실행 기록 | 응답 수 | 쓰임 |
| :--- | :--- | ---: | :--- |
| 게이트 기준선 (채택 구성) | `data/results/v14/baseline/v14_dev_m2_seed{1,11,21}_baseline.json` | 3 × 126 | 채택 구성의 칸별 정답률·Critical 누락을 v1.4와 v1.5로 비교 |
| 실험 A (방법 비교) | `data/results/v14/compare_a.json`의 `runs` 9개 (M0·M1·M2 × seed 3) | 9 × 126 | 방법별 지표 비교와 참고 재판정 |
| 실험 B (모델 비교) | `data/results/v14/compare_b.json`의 `runs` 3개 (qwen2.5:7b·gemma4:12b × seed 3) | 3 × 252 | 모델별 지표 비교와 참고 재판정 |
| 최종 평가용 | `data/results/v14/history/v14_final_m2_20261004_224554.json` | 50 | 라벨이 바뀌지 않았음을 확인하고, F08 주의를 적음 |

이전 버전 파일(실행 기록, `score_*.json`, `compare_*.json`, `gate_result_v14.json`, `report/eval_v14*.md` 등)은 읽기만 하고 고치지 않는다. 기존 `uv run triage-score`는 `report/eval_v14.md`를 덮어쓰므로 이번 작업에 쓰지 않는다.

## 3. 방법

- 새 도구 `src/triage_eval/pipeline/rescore.py` (`uv run triage-rescore`).
- 채점은 기존 함수를 그대로 쓴다: 응답 채점 `score.score_one`, 집계 `score.aggregate`·`gate.counts`, 비교 판정 `compare.compare_seed`·`selection.summarize`·`selection.decide`. 채점 규칙을 새로 만들면 v1.4 결과와 같은 자로 비교할 수 없기 때문이다.
- 같은 실행 기록을 v1.4 평가셋(`data/eval_v14/aether_raid_v14.json`)과 v1.5 평가셋(`data/eval_v15/aether_raid_v15.json`)으로 각각 채점한다. 실행 기록의 `dataset_version`(v1.4)과 다른 라벨로 채점하는 것은 이 도구에서만 의도적으로 허용한다. 그 대신 두 평가셋의 문항 ID와 입력이 완전히 같은지 먼저 확인한다(§5 V0). 입력이 같아야 "모델이 본 리포트에 v1.5 정답을 대조한다"는 말이 성립한다.
- 출력은 새 파일만 만든다: `data/results/v15/rescore/rescore_v15.json`(기계 판독용), `report/rescore_v15.md`(사람이 읽는 표).

## 4. 지표

모두 v1.4 라벨 값과 v1.5 라벨 값을 나란히 적고 차이를 함께 적는다.

| 지표 | 정의 | 쉽게 말하면 |
| :--- | :--- | :--- |
| 칸별 정답률 허용 / 최선 | 6칸(분류·우선순위·모듈·재현 정보·발생 빈도·처리)별. `score.py` 정의 그대로 | 허용 범위 안에 든 비율 / 가장 바람직한 답을 고른 비율 |
| 전 칸 정답 | 6칸이 모두 허용 답 안에 있는 응답 비율 | 리포트 한 건을 통째로 맞힌 비율 |
| X-1·X-2·X-3 누락 / 측정 응답 | `score.py` 정의 그대로. 분모도 라벨에서 나오므로 함께 적는다 | Critical 누락 등 위험 건 수. 분모가 바뀌므로 건수만 보면 오해한다 |
| 과잉 상신 | 허용 답에 없는데 긴급 사인 요청으로 보낸 응답 | 리드 QA 사인 큐를 불필요하게 채운 건수 |
| 변화 상세 | 라벨 변경 때문에 오답→정답, 정답→오답으로 바뀐 응답 수(칸별), 위험 건 판정이 바뀐 문항 | 숫자 차이가 어느 문항에서 나왔는가 |

날조·형식·지연은 라벨과 무관하므로 비교 표에 넣지 않는다(§5 V3에서 같다는 것만 확인한다).

- 게이트 기준선: seed별 값과 seed 3개 합계를 적는다.
- 실험 A·B: 비교 대상(방법/모델)별 seed 3개 합계를 적는다.
- 최종 평가용: v1.4 = v1.5임을 적고, 아래 F08 주의를 붙인다.

아래 중 하나라도 어긋나면 도구 결함으로 보고 결과를 쓰지 않는다(종료 코드 2, 파일 쓰지 않음).

| 번호 | 확인 | 이유 |

| V1 | v1.4 라벨로 다시 채점한 값이 저장된 값과 정확히 같다 — 최종 평가용 `score_v14_final_m2_20261004_224554.json`의 집계, `gate_result_v14.json`의 seed별 기준선 집계, `compare_a.json`·`compare_b.json`의 seed별 판정·합계·채택 결과 | 같은 자로 다시 쟀을 때 같은 값이 나와야 v1.5 값의 차이를 라벨 탓으로 볼 수 있다 |
| V2 | 최종 평가용은 v1.4 라벨 채점과 v1.5 라벨 채점이 응답 단위로 같다 | 최종 평가용 라벨은 바꾸지 않았다 |
| V3 | v1.4와 v1.5 채점 결과가 다른 응답은 모두 라벨이 바뀐 33문항(`changed_ids_v15`)에 속하고, 날조·형식·지연은 모든 응답에서 같다 | 바뀌지 않은 문항에서 차이가 나면 채점 경로가 라벨 말고 다른 것을 읽고 있다는 뜻이다 |

## 6. 해석 규칙 (사전 등록)

- 이 단계는 합격·불합격을 판정하지 않는다. 값을 기록한다.
- **사전 등록 판정은 바꾸지 않는다.** M2 채택(실험 A), qwen2.5:7b 유지(실험 B), 게이트 PASS는 v1.4 라벨로 사전 등록 기준에 따라 내린 판정이며 그대로 둔다.
- **실험 A·B 참고 재판정** — `method_selection_v14.toml` 기준을 그대로 써서 v1.5 라벨로 판정을 다시 계산한다. 목적은 "v1.4의 채택 판정이 라벨 변경에 흔들리는가"를 보는 것이다. 결과는 "참고"로만 적는다. 판정이 달라지더라도 채택을 되돌리지 않고, 그 사실을 기록한 뒤 다음 단계 계획에서 다룬다.
- **F08 주의** — 최종 평가용 F08(로비 화면 멈춤, 앱 재실행 필요, 누를 때마다)의 라벨은 v1.4 그대로(Major·등록(재현 대기))다. v1.5 기준서의 앱 재실행 규칙으로는 Critical·긴급 사인 요청에 해당한다. 최종 평가용은 v1.4에서 이미 사용한 세트라 라벨을 고치지 않았으므로(`docs/dataset/review_log.md`), 최종 평가용 결과를 인용할 때 이 차이를 함께 적는다. 보고서에는 모델이 F08에 낸 우선순위·처리를 사실로만 적고, 다시 채점하지 않는다.
- 차이가 큰 칸이 나와도 이 단계에서 프롬프트·방법·안전장치를 바꾸지 않는다.
