# 서비스 설계 — 링크 접수부터 BTS 등록, QA 업무까지

상태: v2.0 — 설계 단계 S1~S6 구현 완료. 단계별 경위는 [`CHANGELOG.md`](../CHANGELOG.md), 코드 단위의 "왜"는 각 파일 맨 위 `[설계 의도]`에 있다.

## 1. 목표

평가 체계로 검증한 트리아지 파이프라인을 사내에서 쓰는 서비스로 만든다.

- **접수·트리아지·등록**: 리포트 링크를 넣으면 본문을 가져와 트리아지하고, 사람이 8칸을 확인·수정한 뒤 BTS에 등록한다.
- **QA 업무**: QA가 BTS를 따로 열지 않고 배정 → 재현 확인 → 회귀 테스트 → 종료를 서비스 안에서 처리한다.
- **현황**: QA팀 대응 현황(마일스톤·스프린트·병목·부하)과 트리아지 품질을 화면으로 본다.

세 가지 원칙을 지킨다.

1. **출처와 BTS는 파일 한 단위로 바꿔 끼운다.** 회사마다 BTS(Jira, Redmine, 사내 도구)와 리포트가 올라오는 곳(게시판, 디스코드, 커뮤니티)이 다르다.
2. **BTS가 원본이다.** 개발자는 계속 BTS에서 일하므로 서비스가 자체 이슈 목록을 가지면 같은 버그의 상태가 두 곳에서 달라진다. 서비스는 BTS를 읽어 오고, 정해진 동작만 BTS에 쓴다.
3. **사람이 병목이다.** 긴급 사인 요청(판정 기준서 §0)을 빼면 배정·이월은 사람 손 없이 규칙으로 돈다. 사람은 규칙의 결과를 바꿀 수 있다. 다만 트리아지 결과는 v1.5 측정 결과에 따라 모든 건을 사람이 확인한다(자동 등록 라우팅 미채택).

| 구분 | 지원 대상 |
|---|---|
| 출처 (링크) | Jira·Redmine 이슈, 게시판 글(사이트별 설정), 디스코드 메시지(회사 봇), 본문 붙여넣기 |
| BTS | Jira Cloud, Redmine, 가짜 BTS(시험·시연용) |

## 2. 구조

```
[링크] → 접수 ─ 출처 어댑터 → Report → 트리아지 → 검토(사람) → 등록·배정 ─ BTS 어댑터 → Jira / Redmine
                                                                              ↑ 읽기(동기화) · 쓰기(QA 동작·접수·이월)
                                                  홈 · 내 업무 · 대시보드 · 트리아지 품질
```

서비스 코드는 `src/triage_service/`에 있고, 측정한 트리아지 함수(`triage_eval.triage.pipeline.triage`)를 그대로 호출한다. 모델·생성 옵션은 평가 패키지 설정을 따른다.

### 계약 (`contracts.py`)

| 계약 | 함수 | 의미 |
|---|---|---|
| `Source` | `matches(url)` · `canonical(url)` · `fetch(url) -> Report` | 이 링크를 처리하는가, 같은 원문 링크를 하나로 맞춘 모양, 제목·본문·작성 시각 가져오기 |
| `Tracker` | `find(ref)` · `create(issue) -> Ticket` | 서비스 표식으로 기존 티켓 찾기, 등록(팀·담당자·마일스톤·스프린트 포함) |
| | `status(key)` · `snapshot(keys)` | 단건 상태(쓰기 전후 확인용), 여러 건의 상태·담당자·변경 시각 |
| | `update(key, status, team, comment, assignee, sprint)` | 상태·팀·코멘트·담당자·스프린트 바꾸기(빈 값은 그대로). 언제 무엇을 쓸지는 `qa.py`·`sync.py`가 정한다 |
| | `versions()` · `milestone_tickets(version)` | 마일스톤(BTS 버전) 목록, 한 버전의 티켓 전체(팀·스프린트 표식 포함) |
| | `members(team)` · `lead(team)` · `open_count(member)` · `me()` | 팀 그룹 구성원, 팀장, 한 사람의 미해결 수, 토큰 주인 |
| | `check_assignees()` · `check_statuses()` | 연결 확인(`--check`): 그룹·구성원·팀장, 다섯 상태 |

- BTS 상태 이름은 서비스와 BTS가 같은 다섯 개(`STATUSES`)를 쓴다. 아직 끝나지 않은 넷은 `OPEN` 한 곳에서 정한다.
- 우선순위·이슈 유형·팀 → 그룹 같은 BTS별 값은 코드가 아니라 `설정/bts_매핑.toml`에 둔다.
- 세 어댑터(가짜·Jira·Redmine)는 실제 서버에서 녹화한 응답(`tests/bts_responses/`, 인증 정보·사이트 주소 제거)으로 같은 계약 시험을 통과한다.

### 영역 (관심사 분리)

| 파일 | 책임 |
|---|---|
| `contracts.py` | 영역 사이에 주고받는 타입과 계약, 상태 이름 |
| `config.py` | 서비스 설정 한 곳 — DB 위치, 접속 주소, 입력 길이, 동기화 간격, 병목 기준, 스프린트 요일·주 수 |
| `intake/` | 출처 어댑터(붙여넣기·BTS 이슈·게시판·디스코드), 허용한 곳만 요청(`fetching.py`), 출처 설정 검사, 접수 흐름(`reception.py`) |
| `worker.py` · `routing.py` · `flow.py` | 작업자 하나가 차례대로 트리아지, 자동 등록 결정(미채택 — 전부 검토), 리포트 상태 흐름 |
| `review.py` | 사람이 확정한 8칸을 형식 규칙(R1~R7)으로 검사해 등록·폐기, 마일스톤·스프린트 입력 검사 |
| `assign.py` | 자동 배정 — 받을 팀과 그 그룹에서 미해결이 가장 적은 구성원, 첫 상태 |
| `qa.py` | QA 동작 — 재현 확인·사인·회귀 테스트 통과·실패·보류·코멘트를 BTS에 쓰고 기록 |
| `sync.py` | 동기화(읽기), Resolve 접수·스프린트 이월(동기화가 하는 두 가지 쓰기), 내 업무 목록 |
| `sprint.py` | 스프린트 날짜 규칙(기준 업데이트, 우선순위별 기본 목표) |
| `metrics.py` | 지표 계산 — 마일스톤 성과, 홈의 QA Review 표, 대응 흐름·병목, 스프린트 현황, 트리아지 품질 |
| `store.py` | SQLite — 리포트(모델 8칸·확정 8칸·고친 칸·배정), 상태 이력, QA 동작 기록, 마일스톤 티켓과 상태 변화, 이월 기록 |
| `bts/` | BTS 어댑터, 접속 클라이언트(`clients.py` 한 곳), 설정·토큰 검사 |
| `auth.py` | 로그인 — 사람별 계정(사용자 파일·scrypt 해시) 또는 망 접속 시연용 공용 비밀번호, 실패 제한, 사용자를 담은 서명 쿠키 |
| `web/` | FastAPI 라우트 + Jinja2. 규칙 없이 각 영역의 결과를 보여 주기만 한다 |
| `cli.py` | `uv run triage-serve [--check \| --lan]` — `--lan`은 이 PC의 망 주소를 모두 찾아 휴대폰으로 열 주소와 QR 코드를 보인다(유선·와이파이에 함께 붙은 노트북은 주소가 여럿이라 주소별 QR, 네트워크 카드 이름으로 휴대폰용·PC용·가상 망을 구분해 적는다) |

## 3. 화면

화면의 디자인·구성 요소·메뉴별 내용과 변경 이력은 [화면 설계](화면_설계.md)에 따로 둔다. 메뉴는 홈(QA 업무 현황) · 내 업무(지금 처리할 일·새 리포트·넘긴 이슈) · 리포트 · 대시보드(병목·부하 분석) · 트리아지 품질 다섯 개다.

- 망 접속 모드에서는 로그인 화면(`/login`)과 휴대폰 접속 화면(`/connect`, 주소별 QR 코드)이 생기고, 머리에 [휴대폰 접속]·[로그아웃]이 보인다. 화면은 375px 폭에서 가로 스크롤 없이 읽힌다.
- 모든 화면 머리에 BTS 연결 표시("● Jira 연결됨 · 3분 전")가 있다. BTS를 따로 부르지 않고 마지막 동기화 결과로 정하며, 언제 읽은 값인지 함께 보여 숫자를 얼마나 믿을지 판단하게 한다.
- 서버 렌더링(FastAPI + Jinja2)만 쓴다. Python 하나로 유지보수하고, 프런트 빌드·외부 CDN이 없어 사내망에서 그대로 돌고, 토큰이 서버 밖으로 나가지 않는다. 막대 그래프는 HTML·CSS로 그린다. 디자인 값은 `base.html`의 `:root`에만 둔다.

## 4. 업무 규칙

### BTS 상태 다섯 단계

| 상태 | 뜻 | 서비스에서 |
|---|---|---|
| QA Review | QA가 재현을 확인하는 중 | 재현 대기 — [재현 확인](→ In Dev, 개발팀으로), 긴급 사인 요청은 QA팀장의 [사인 후 개발 전달] |
| In Dev | 개발이 고치는 중 | 개발이 BTS에서 Resolve로 바꾼다 |
| Resolve | 수정 완료, 회귀 테스트 필요 | 회귀 테스트 대기 — 통과(→ Closed), 실패(→ In Dev, 개발팀 구성원에게) |
| Check | 사유가 있어 대응 보류(사유 코멘트 필수) | 보류 |
| Closed | 대응 종료 | — |

새 티켓의 첫 상태는 [처리]로 정한다: 등록(재현 대기)·정보 요청 후 보류·긴급 사인 요청 → QA Review, 개발 배정 → In Dev, CS 응대 → QA 재현이 필요하면 QA Review 아니면 Check(사유 코멘트). 재현 필요 여부의 기본값은 [분류]가 결함인지이고 검토 화면에서 바꾼다.

### 자동 배정

- **팀 = BTS 그룹, 담당 = 그 그룹 구성원 한 사람.** 구성원 중 이 프로젝트의 미해결이 가장 적은 사람이 받는다(같으면 서비스가 가장 오래전에 배정한 사람). 팀장도 구성원으로서 받는다.
- **받는 팀:** 등록(재현 대기)·정보 요청 후 보류 → QA팀, 개발 배정 → 첫 [모듈]의 팀(모듈이 없으면 QA팀), CS 응대 → CS팀(QA 재현이 필요하면 QA팀), 폐기 → 배정 없음. [처리]가 받는 쪽을 정하는 것은 8칸 형식의 뜻이라 코드에, 팀 이름과 모듈 → 팀 표는 설정에 둔다.
- **긴급 사인 요청은 QA팀장이 받는다**(판정 기준서 §0 "Critical은 리드 QA 사인을 거친다"). 팀장만 [사인 후 개발 전달]을 누를 수 있고, 누르는 사람은 BTS 토큰 주인으로 확인한다. 검토 화면에서 다른 팀을 골라도 긴급 사인 요청은 QA팀장에게 간다.
- QA팀으로 간 이슈는 처음 받은 사람을 QA 담당(`qa_owner`)으로 기억해, 개발을 거쳐 Resolve가 되면 그 사람의 회귀 테스트 차례가 된다.
- 사람은 검토 화면에서 팀·담당자를 바꿀 수 있고, 규칙의 결과와 함께 저장해 "사람이 바꾼 배정" 비율로 센다.

### QA 동작

- 동작마다 할 수 있는 상태가 정해져 있다. 화면은 마지막 동기화 값이므로 **쓰기 직전에 BTS 상태를 다시 읽고**, 그사이 바뀌었으면 보내지 않는다.
- **쓴 뒤 단건 조회로 다시 읽어** 목표 상태가 됐는지 확인한다. 실패하거나 일부만 된 것도 그대로 기록(`qa_actions`)하고 상세 화면에 보인다. 대체 처리는 하지 않는다.
- 재현 확인·회귀 실패·보류·코멘트는 사유 코멘트가 필요하다. BTS 코멘트 앞에 `[트리아지 서비스 · 동작]`을 붙인다.
- **회귀 테스트 실패**는 In Dev로 돌리며 담당을 지금 담당 팀 그룹의 미해결이 가장 적은 사람으로 바꾼다. 담당이 QA에 남으면 개발이 알림을 못 받기 때문이다.

### 동기화

- **끌어오기만 한다.** 서비스가 이 PC(127.0.0.1)에서만 열려 있어 BTS의 웹훅을 받을 수 없다. [지금 동기화] 버튼(홈)과, 홈·내 담당·대시보드를 열 때 마지막 동기화가 10분(`AUTO_SYNC_MINUTES`)보다 오래됐으면 뒤에서 읽는다. 화면은 기다리지 않는다.
- 읽는 것: 서비스가 등록한 최근 200건의 상태, 출시 전 마일스톤의 티켓 전체(팀·스프린트 표식 포함), 토큰 주인. 한 묶음이 실패해도 나머지는 갱신하고, 이전 값을 지우지 않는다.
- 동기화·등록·QA 동작은 **잠금 하나** 안에서 한 번에 하나씩 한다. 동기화가 읽어 둔 옛 상태가 QA 동작이 쓴 새 상태를 덮어쓰지 않게 하려는 것이다.
- **동기화가 BTS에 쓰는 경우는 두 가지뿐이다.**
  1. **Resolve 접수** — 서비스가 등록했고 QA 담당이 없는 건(바로 개발 배정)이 Resolve가 되면 QA팀 구성원 중 미해결이 가장 적은 사람에게 배정한다. 그러지 않으면 회귀 테스트가 아무에게도 오지 않는다.
  2. **스프린트 이월** — 아래 마일스톤과 스프린트 참고.
- 두 쓰기 모두 한 번만 하고(기록이 있으면 건너뜀), 쓰기 직전에 상태를 다시 읽고, 실패하면 다음 동기화에서 다시 시도한다.

### 마일스톤과 스프린트

- **마일스톤(월간) = BTS 버전**(Jira 릴리스, Redmine 목표 버전). 두 BTS에 공통으로 있는 단위다. 성과는 서비스가 등록한 건이 아니라 그 버전의 BTS 티켓 전체로 센다. 검토 화면에서 출시 전 마일스톤을 고른다.
- **스프린트(주간) = 목표 수정 버전.** 매주 목요일(`SPRINT_WEEKDAY`) 정기 업데이트 하나가 스프린트이고, 이슈마다 "어느 업데이트에서 고칠지"를 단다.
  - 기본 목표: 발견한 날 다음 업데이트(업데이트 날 발견하면 다음 주)에서 우선순위별로 Critical 0주·Major 1주·Minor 2주·Trivial 3주 뒤(`SPRINT_WEEKS`). 긴급 사인 요청은 다음 업데이트. 지난 업데이트는 고를 수 없다.
  - BTS 표식: Jira `스프린트_<날짜>` 라벨, Redmine 날짜 사용자 정의 필드(`sprint_field_id`). 개발자도 BTS에서 보고 바꾼다. Jira 스프린트 기능은 Redmine에 없어 쓰지 않는다.
  - **이월:** 목표 업데이트가 지났는데 Closed가 아니면(Check 포함) 동기화가 진행 중인 업데이트로 옮기고 BTS 코멘트(`이월 N회`)와 기록(`sprint_carries`)을 남긴다. 업데이트 날은 진행 중이라 다음 날부터 대상이다. 2회 이상 이월된 이슈는 대시보드에 병목으로 보인다.

### 지표

- 비율은 언제나 분자·분모를 함께 보이고(분모 0이면 "데이터 없음"), 백분위는 nearest-rank다.
- 상태 변화 시각은 BTS가 바꾼 때가 아니라 **동기화가 발견한 때**다. 처음 읽었을 때 이미 그 상태였던 건처럼 시각을 모르는 건은 빼고 그 건수를 적는다.
- 병목 기준(`BOTTLENECK_DAYS`: QA Review 2일·In Dev 7일·Resolve 2일·Check 14일)과 머문 일수 계산은 홈·내 업무·대시보드가 같은 것을 쓴다.
- 대시보드(QA 리드: "지금 어디서 막혔나")와 트리아지 품질(모델 운영: "모델이 얼마나 맞히나")은 보는 사람과 질문이 달라 화면을 나눴다.

## 5. 안전장치

| 위험 | 대응 |
|---|---|
| 토큰 유출 | BTS·디스코드 토큰은 `.env`에만 두고 로그·화면·녹화 응답에 남기지 않는다 |
| 임의 주소 요청(SSRF) | 설정에 적은 호스트·경로의 링크만 요청하고, 리다이렉트를 따라가지 않고, 응답 크기에 상한을 둔다 |
| 외부 접속·요청 위조 | 평소에는 127.0.0.1에서만 받고, Host가 허용 목록 밖이거나 다른 사이트에서 온 POST(Origin·Referer)는 거절한다. 망 접속 모드(`--lan`, 시연용)는 같은 와이파이의 휴대폰을 받되, 이 PC의 와이파이 주소만 허용 목록에 더하고 로그인하지 않은 요청은 로그인 화면으로 보낸다. 비밀번호는 `.env`의 공용 시연 비밀번호(8자 이상), 같은 기기에서 1분에 5번 넘게 틀리면 잠시 막고, 로그인 쿠키는 서버를 켤 때마다 새 키로 서명해 12시간 유효하다. 통신은 HTTP라 시연 데이터만 쓰는 전제다 |
| 프롬프트 주입 | 리포트 본문은 입력 데이터로만 다룬다. 출력은 형식 계약과 안전장치를 통과해야 하고, 사람이 모든 응답을 확인한다 |
| 개인정보·수집 제약 | 작성자 닉네임은 가져오지 않는다. DB는 git에 올리지 않는다. 디스코드는 회사 봇이 설치된 서버만 읽고, 외부 커뮤니티는 이용 약관·robots를 확인한 뒤 설정에 넣는다 |
| 측정과 다른 입력 | 서비스 입력은 평가셋 문항과 같은 모양으로 만들고(시험으로 고정), QA 이슈 작성자는 평가셋에 쓰인 값만 받는다 |
| 사람 구분 | 사용자 파일(`설정/사용자.local.toml`)이 있으면 사람마다 로그인한다(이 PC 포함). 비밀번호는 scrypt 해시로만 적고, 없는 이름도 같은 시간이 걸리게 비교한다. 내 업무와 긴급 사인 확인은 로그인한 사람의 BTS 계정으로, 등록·QA 동작에는 누른 사람을 남긴다(BTS 코멘트 "(실행: 이름)"). 역할: 리더(팀장·파트장)만 대시보드·트리아지 품질·팀원 업무 보기·긴급 사인·담당 바꾸기를 하고, 실무자는 모든 이슈에 QA 동작을 할 수 있다(서로 돕고 대신 맡도록). 메뉴와 서버가 같은 권한 표(`auth.LEADER_ONLY`)를 써서 주소를 직접 쳐도 거절한다 |
| 중복 등록 | 같은 원문 링크는 한 번만 접수하고, 등록 전에 서비스 표식으로 기존 티켓을 찾는다. 응답이 끊기면 "등록 여부 불확실"로 남기고 자동으로 다시 보내지 않는다 |
| 실패 은폐 | 가져오기·트리아지·등록·QA 동작의 실패는 그대로 남기고 대체 데이터를 만들지 않는다. 트리아지 실패는 [다시 시도]로 처음부터, 등록 실패는 [검토로 되돌리기]로 확정한 8칸을 둔 채 다시 등록한다(모델을 다시 돌리지 않음). Jira는 등록 직후 검색에 늦게 나타날 수 있어, 응답이 끊긴 직후에는 Jira에서 먼저 확인한 뒤 다시 등록한다 |
| 잘못된 설정 | 모르는 키, 빠진 대응, 없는 토큰이 있으면 서버가 시작하지 않는다. `--check`가 그룹·구성원·팀장·다섯 상태를 확인하고, QA팀 그룹에 같은 표시 이름이 있으면 경고한다 |

## 6. Jira와 Redmine의 차이와 맞춘 방법

| 항목 | Jira Cloud | Redmine 6.0 | 서비스가 맞춘 방법 |
|---|---|---|---|
| 팀·모듈 표시 | `팀_<이름>`·`모듈_<이름>` 라벨 | 일감 범주(팀), "모듈" 사용자 정의 필드 | 두 BTS 모두 팀·모듈로 걸러 볼 수 있게 표식을 넣는다 |
| 담당 | 그룹을 담당자로 둘 수 없음 | 그룹 배정 가능 | 둘 다 그룹 구성원 한 사람에게 배정 |
| 여러 건 읽기 | 검색(`/search/jql`)이 색인이라 방금 바뀐 값이 몇 초 늦음 | DB를 바로 읽음 | Jira는 최근 다룬 이슈 ID를 `reconcileIssues`로 함께 보내 최신 값으로 읽는다. 미해결 수도 같은 방식으로 센다 |
| 상태 이름 | 한국어 계정에서 Closed가 "종료"로 번역됨 | 이름 그대로 | Jira는 완료 범주 상태를 Closed로 읽는다(워크플로에 완료 범주는 하나) |
| 쓰기 | 담당자·라벨, 상태(전환), 코멘트를 따로 보냄 | PUT 한 번(워크플로가 막으면 상태만 무시될 수 있음) | 둘 다 쓴 뒤 단건 조회로 확인한다 |
| 그 밖 | 팀 관리형 공간은 이슈 유형 "작업", 릴리스는 보기(+)에서 켜야 함 | 그룹 구성원 읽기에 관리자 API 키 필요 | 이슈 유형·우선순위·필드 번호는 설정 파일에 둔다 |

## 8. 남은 한계

- **망 접속 모드는 시연용이다.** 공용 비밀번호 하나라 누가 눌렀는지 구분하지 않고, 통신을 암호화하지 않고, 로그아웃해도 이미 복사된 쿠키는 서버를 끌 때까지 유효하다. 기기끼리 막은 와이파이(카페 등)에서는 접속되지 않는다. 여러 사람이 실제 업무로 쓰려면 사람별 계정·HTTPS가 먼저다.
- **BTS 화면의 변경자는 공용 계정이다.** BTS에 쓰는 토큰은 서비스 공용이라, 누가 했는지는 서비스 기록과 BTS 코멘트의 "(실행: 이름)"으로 안다. 역할은 리더·실무자 두 가지뿐이다(파트별 범위는 두지 않음).
- **한 사람이 이 PC에서 쓰는 전제다.** 담당자·내 업무는 BTS 표시 이름으로 비교해 이름이 같은 두 사람을 구분하지 못한다(`--check`가 QA팀 안의 같은 이름을 경고한다). 같은 티켓을 BTS 화면에서 동시에 바꾸는 것은 막지 못하고, 쓴 뒤 다시 읽어 결과를 보이는 것으로 대신한다.
- **시각은 동기화가 발견한 때다.** 동기화 사이에 Resolve → In Dev → Resolve가 오가면 재오픈을 놓치고, 목요일이 지난 뒤 처음 동기화할 때 이월된다. 마지막 동기화 시각은 서버 메모리에만 있다.
- **마일스톤 밖은 세지 않는다.** 마일스톤 성과·스프린트·대응 흐름은 출시 전 마일스톤의 티켓만 읽는다(마일스톤당 500건까지). 티켓 하나는 마일스톤 하나로 센다.
- **"넘긴 이슈"는 QA팀을 거친 건만 나온다.** 바로 개발로 배정한 건은 등록자 기록이 없다. 회귀 실패로 돌려받는 개발자는 처음 고친 사람이 아닐 수 있다(그 시점 미해결이 가장 적은 사람).
- **디스코드 실제 봇 연결 전이다.** 회사 봇 토큰(`DISCORD_BOT_TOKEN`)이 있어야 켜진다. 외부 커뮤니티 게시판은 이용 약관·robots 확인 전이라 로컬 견본으로만 확인했다.

## 10. QA 실무 경험과 부트캠프 학습의 활용

- **QA 실무**
  - 라이브 서비스에서 리포트는 게시판·디스코드·커뮤니티로 들어와 사람이 BTS로 옮겨 적는다. 이 옮겨 적기와 1차 분류를 자동화하되 등록 직전에 사람이 확인하는 지점을 남긴 것은 오등록 비용이 크다는 실무 판단이다.
  - BTS가 회사마다 다르다는 경험이 어댑터 구조의 근거다.
  - 재현 확인 → 개발 → 회귀 테스트 → 종료, Critical은 리드 QA 사인 후 전달, 보류는 사유 코멘트, 매주 정기 업데이트에 고칠 이슈를 싣는 방식은 QA 업무 흐름을 그대로 옮긴 것이다. 회귀 테스트가 누구에게도 가지 않는 건(바로 개발 배정)을 막은 것도 실무에서 겪는 누락이다.
- **KANT AI 부트캠프 Private LLM 트랙**
  - FastAPI 계약 설계: 데이터 파이프라인·FastAPI 과목.
  - 신뢰 경계·개인정보 가리기·출력 검증: LLMOps 4장.
  - 운영 지표(p95·오류율·분모 표기): LLMOps 3장.
  - 입력 정리 순서와 토큰 예산: 컨텍스트 엔지니어링.
  - 수집 전 리스크 점검: 데이터 수집 과목.
  - 영역별 계약(`contracts.py`)과 설정 한 곳(`config.py`): 3차 팀 프로젝트의 구조.
