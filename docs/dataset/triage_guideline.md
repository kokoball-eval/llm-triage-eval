## 0. 적용 범위

가상 게임 "Aether Raid"(모바일 + PC 크로스플랫폼 RPG)에 들어오는 이슈를 두 트랙으로 판정합니다.

| 트랙 | 입력 | 판정의 목적 | 실무 비중 (근거: 1차 Q2) |
| :--- | :--- | :--- | :--- |
| **A. 커뮤니티 제보** | 유저가 커뮤니티·공식 홈페이지에 쓴 원문 | 걸러내기 — 등록할 것, 정보를 더 받아야 할 것, 버릴 것을 가른다 | BTS 인입의 약 5% (걸러지기 전 원문은 훨씬 많음) |
| **B. QA 작성 이슈** | 내부·퍼블리셔 QA가 양식대로 쓴 BTS 이슈 | 우선순위 제안과 작성 품질 점검 | BTS 인입의 약 95% |

**이슈 생명주기 (근거: 2차 C2, 3차 Q3)**

```text
[트랙 A] 커뮤니티 제보 ─▶ 운영/CS가 BTS 등록 ─┐
[트랙 B] 내부·퍼블리셔 QA가 BTS 등록 ─────────┤
                                              ▼
                     개발 QA: 재현 확인 → 대응 여부 결정
                                              ▼ (대응 시)
                         수정 → 수정 확인 → 빌드에 태워 전달
                                              ▼
                       운영/CS(또는 등록한 QA) 최종 확인 → 종료
```

**자동화가 대신하는 범위** — 트랙 A에서는 **운영/CS의 등록 단계**(원문을 읽고, 거르고, 티켓을 쓰는 일), 트랙 B에서는 **우선순위 제안과 작성 품질 점검**입니다. **재현과 대응 여부 결정은 대신하지 않습니다.** 실무에서 모든 이슈는 개발 QA가 재현한 뒤 대응을 결정했으므로, 트랙 A에서 자동 등록된 티켓은 "재현 대기" 상태로 들어갑니다. 트랙 B는 QA가 이미 재현을 확인했으므로 개발팀에 바로 배정합니다(H-2b).

**Critical은 리드 QA 사인을 거친다 (근거: 전체 검토 2차 확인 1)** — 자동화는 Critical 후보를 개발팀에 직접 보내지 않습니다. `[처리] 긴급 사인 요청`은 **리드 QA에게 즉시 알려 사인을 받은 뒤** 개발팀에 전달한다는 뜻입니다. 실무에서도 Critical 전달은 리드 QA만 사인했고, 리드 부재 시에는 업무 프로세스상 지정된 대리 업무자가 그 역할을 맡으므로 사인 담당자는 항상 있습니다. 가장 위험한 판정에만 사람이 서명하는 구조라, Critical은 자동 처리율에 넣지 않습니다.

## 1. 출력 필드

| 필드 | 선택지 | 설명 |
| :--- | :--- | :--- |
| `[요약]` | 자유 서술 1줄 | 입력에 있는 사실만으로 쓴다 (v1.2 환각 탐지 대상) |
| `[분류]` | 결함 / 개선 제안 / 버그 아님 / 문의·건의 / 중복 의심 / 무관 | §2 |
| `[모듈]` | 10개 판정 모듈 중 택1 (복합 시 병기) | §3 |
| `[우선순위]` | Critical / Major / Minor / Trivial / 판단보류 / 해당 없음 | §4. 결함·개선 제안은 우선순위를 매기고, 중복 의심은 **기존 이슈의 우선순위**를 따른다. 그 밖의 분류는 "해당 없음" (전체 검토 3·8·10). 단, 부정행위 신고처럼 **결함 여부를 확인하기 전인 문의·건의**는 판단보류도 허용 (v1.5 검토) |
| `[재현 정보]` | 충분 / 부족 | §5. 재현 성공 여부가 아니라 "재현을 시도할 정보가 있는가" |
| `[발생 빈도]` | 항상 / 간헐적 / 1회 / 미기재 / 해당 없음 | §5.1. 리포트에 **적힌** 빈도를 옮긴다. **해당 없음**은 결함 현상을 다루지 않는 글(무관, 개선 제안, 순수 문의·건의), 부정행위 신고처럼 **현상은 있는데 빈도가 없으면 미기재** (전체 검토 5차) |
| `[처리]` | 긴급 사인 요청 / 등록(재현 대기) / 개발 배정 / 정보 요청 후 보류 / CS 응대 / 폐기 | §6. 등록(재현 대기)은 트랙 A, 개발 배정은 트랙 B와 개선 제안(H-2d). 긴급 사인 요청은 리드 QA 사인 후 개발 전달(§0) |
| `[누락 정보 및 권장 조치]` | 자유 서술 | 재현에 필요한데 빠진 정보, QA 권장 조치 |

- **해석:** v1.0의 `[재현 여부]`(발생(100%) / 간헐적 / 불명확 / 재현 불가)는 `[재현 정보]`로 바꿨습니다. 모델은 리포트만 보고 재현 성공 여부를 알 수 없고, 실무에서도 재현은 사람이 했기 때문입니다(2차 C2). 대신 리포트에 적힌 빈도는 모델이 옮길 수 있으므로 `[발생 빈도]`로 따로 둡니다(전체 검토 2차 확인 5).

| C-6 | 감정적 불만이라도 그 안에 결함 정보가 있으면 결함 부분을 판정한다 | 해석 (2차 A1에서 감정적 불만 24%가 무관 30%와 따로 집계됨) |

| C-8 | **다른 유저의 부정행위 신고**(부계정 승점 몰아주기, 핵 사용, 매크로 등)는 행위자 제재가 목적이면 **문의·건의**(CS 응대). 개발사가 대응할 사항이 아니다(7차 Q2 확인). 단, 신고 내용에 **시스템이 막지 못하는 방법**(재현 가능한 악용 절차)이 들어 있으면 그 부분은 **결함**으로 판정 | 해석 (4차 사례 2, 사례 1·5와 대비) |
| C-8b | 부정행위 신고라도 **시스템 구조의 허점**(예: 저인원 시간대에 같은 길드·부계정끼리 매칭되는 규칙)을 고쳐야 막을 수 있으면 **개선 제안**으로 등록해 개발이 대응하고, 행위자 제재 요청은 운영/CS에 따로 넘긴다. 매크로처럼 제재로 해결되는 신고는 C-8. **대비 예시:** 핵·매크로 사용자 제재 요청 → C-8(문의·건의, CS 응대) / 저인원 시간대 매칭 규칙의 허점 → C-8b(개선 제안) / 보상 수령 중 네트워크를 끊어 중복 수령 → C-8 단서(결함) | 8차 Q3, v1.5 검토 |
| C-9 | **같은 상황에서 동시에 발생하는 여러 현상**(예: 전화 수신 후 사운드 끊김 + 화면 멈춤)은 이슈를 나누지 않고 **하나의 결함으로 판정**한다. 우선순위는 가장 심한 현상 기준, 모듈은 병기. **서로 다른 상황의 여러 현상**을 한 글에 쓴 경우에도 우선순위는 가장 심한 현상 기준으로 매기고, 권장 조치에 분할 등록을 적는다 | 7차 Q3, v1.5 검토 |

## 4. 우선순위

### 4.1 기본 기준 (근거: 1차 Q4)

| 등급 | 기준 | 대표 예시 |
| :--- | :--- | :--- |
| **Critical** | 핵심 진행을 완전히 차단하거나 유저 데이터·매출에 치명적. 우회 방법 없음. 출시 전이면 빌드를 멈추고 수정, 라이브면 즉시 핫픽스 | 실행 불가·100% 크래시, 결제 후 재화 미지급 또는 무한 획득, 세이브 데이터 소실·로그인 불가, 메인 퀘스트 진행 불가 |
| **Major** | 핵심 기능·플레이 경험에 큰 지장이 있으나 구동은 되거나 우회 가능. 다음 정기 업데이트 전까지 반드시 수정 | 핵심 스킬 데미지 미적용, 구형 기기 심한 프레임 저하, 서브 퀘스트 완료 불가, 상점 UI가 깨져 가격 식별 곤란 (특정 해상도에서만 겹치면 Minor — 전체 검토 5, 보완) |
| **Minor** | 코어 루프는 정상이나 UX를 해치거나 부가 기능이 의도와 다름. 여유 있을 때 수정, Known Issue로 출시 가능 | 텍스트 오버플로, 효과음 지연, 가벼운 클리핑, 업적 아이콘 오출력 |
| **Trivial** | 플레이 지장 없음. 대부분 눈치채지 못하는 미관상 결함. Won't fix 가능 | 단순 오타·띄어쓰기, 버튼 1~2px 어긋남, 극도로 특이한 조작에서만 나는 시각 오류, 배경 소품 그림자 누락 |
| **판단보류** | 결함으로 보이지만 우선순위를 정할 정보가 부족 | 해석 (v1.0 계약 유지) |
| **해당 없음** | 분류가 결함이 아님 | 해석 |

**Minor와 Trivial의 경계 (v1.4, 2026-10-04):** 두 등급은 모두 코어 루프에 지장이 없고 "여유 있을 때 수정" 대상이라, 서로 바뀌어도 BTS 처리(대기열·일정)가 크게 달라지지 않는다. 판정에서 가장 중요한 경계는 결함인지 아닌지, 그리고 Critical인지 아닌지이다. 그래서 정답이 Minor인 문항은 Trivial도, Trivial인 문항은 Minor도 허용한다. 첫 정답(가장 바람직한 답)은 그대로 둔다.

**앱 재실행 규칙 (v1.5, 2026-10-14):** 버그로 인해 **앱 재실행이 반드시 필요한 현상**(화면 멈춤·터치 무반응·크래시)이 **반복**(발생 빈도 항상·간헐적)되면 **Critical, 긴급 사인 요청**. 재실행 뒤 다른 경로로 우회할 수 있어도 같다. 1회면 F-2대로 Major. 특정 기기에서만 발생하는 것으로 확정되면 P-B3대로 Major·등록(재현 대기)도 허용한다. (근거: v1.5 검토 B17. v1.4 최종 평가용 F08은 이미 사용한 세트라 라벨을 고치지 않고 검토 기록에 남김)

### 4.2 경계 규칙 — 정답이 하나가 아닌 경우 (근거: 1차 Q5)

**P-B6 처리 순서 (근거: 4차 Q3)**
1. 기간제 효과(이벤트 컬렉션·장비) 만료 시점과 겹치면 → 버그 아님 가능성이 높음. 그래도 **개발 QA의 재현 확인(문제 상황 파악)이 먼저**이므로 `등록(재현 대기)`로 보내고, 확인되면 CS 응대(만료 안내) (8차 Q2)
2. 공지(패치 노트)의 조정 내용과 일치하면 → 1과 같이 개발 QA 재현 확인 후 CS 응대 (1에 맞춘 해석)
3. **공지된 수치와 실제 수치가 다르거나**, 공지 없이 바뀌었으면 → 결함 가능성. 테이블 데이터 대조 후 인게임 테스트를 권장 조치에 적고 사람 검토 (테이블 실수로 확인되면 Critical, 핫픽스)
4. 리포트만으로 1~3을 가릴 수 없으면 → 판단보류 + 정보 요청 후 보류 (어떤 능력치가, 언제부터, 기간제 아이템 착용 여부)

**참고 — 수치 의혹 (H-10, v1.5 검토):** 확률 조작·보스 난이도 의혹은 경계 규칙은 아니지만 판정이 자주 갈린다. 무관·폐기·CS 응대로 끝내지 않고 등록(재현 대기)로 보내 개발 QA가 먼저 확인한다(§6.2 H-10). X-3의 범위(P-B1~B6)는 바꾸지 않는다.
