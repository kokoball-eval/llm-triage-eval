# 서비스 설계 — 링크 접수부터 BTS 등록까지

상태: 설계 확정, 구현 전 (v1.5 9단계 판정 이후 착수)

## 1. 목표

평가 체계로 검증한 트리아지 파이프라인을 사내에서 쓸 수 있는 서비스로 만든다.

- **작업 페이지**: 리포트 링크를 붙여 넣으면 본문을 가져와 트리아지하고, 사람이 확인·수정한 뒤 BTS에 등록한다.
- **대시보드**: 이슈 처리 현황과 운영 지표를 보여 준다.

설계 요구는 하나다. **들어오는 곳(출처)과 나가는 곳(BTS)을 코드 한 파일 단위로 바꿔 끼울 수 있어야 한다.** 회사마다 쓰는 BTS(Jira, Redmine, 사내 도구)와 리포트가 올라오는 곳(공식 홈페이지 게시판, 디스코드, 커뮤니티)이 다르기 때문이다.

| 구분 | 지원 대상 |
|---|---|
| 출처 (링크) | 공식 홈페이지 게시판, 디스코드, 커뮤니티 사이트, Jira, Redmine, 본문 붙여넣기 |
| BTS (등록 대상) | Jira, Redmine |

## 2. 구조 — 가운데는 고정, 바깥은 어댑터

```
[링크] → 접수 ─ 출처 어댑터 ─→ Report ─→ 트리아지 ─→ 라우팅 ─→ 흐름 ─→ BTS 어댑터 → Jira / Redmine
                                                                    ↓
                                                         대시보드 (처리 현황·운영 지표)
```

트리아지·라우팅·흐름은 공통 타입(`Report`, `Issue`)만 다루고 출처나 BTS의 종류를 모른다. 출처·BTS의 차이는 어댑터 안에서 끝난다.

### 계약 (`contracts.py`)

| 계약 | 함수 | 의미 |
|---|---|---|
| `Source` | `matches(url) -> bool` | 이 링크를 이 어댑터가 처리하는가 |
| | `fetch(url) -> Report` | 제목·본문·작성 시각·원문 링크를 가져온다 |
| `Tracker` | `create(issue) -> Ticket` | BTS에 등록하고 티켓 번호·링크를 돌려준다 |
| | `status(key) -> str` | BTS에서의 처리 상태를 조회한다 |

- 새 출처·새 BTS는 계약을 구현한 파일 하나를 추가하고 목록(출처) 또는 설정(BTS)에 등록하면 붙는다.
- 우선순위·모듈 같은 값의 BTS 필드 매핑(예: Critical → Jira `Highest`, 결제·재화 → 컴포넌트 `Payment`)은 코드가 아니라 설정 파일에 둔다. 회사마다 다른 필드 이름은 설정으로 맞춘다.
- 모든 어댑터는 같은 계약 시험을 통과해야 한다. 시험은 녹화한 API 응답으로 돌려 실제 서버 없이 CI에서 실행한다.

### 영역 (관심사 분리)

| 영역 | 책임 |
|---|---|
| `contracts.py` | 영역 사이에 주고받는 타입 — `Report`, `TriageResult`, `Issue`, `Ticket` |
| `config.py` | 설정 한 곳 — 모델, 허용 도메인, 사용할 BTS, 매핑 파일 경로 |
| `intake/` | 출처 어댑터 — `jira`, `redmine`, `discord`, `board`(사이트별 선택자는 설정), `paste` |
| `triage/` | 채택 파이프라인(qwen2.5:7b, 프롬프트 v2.3, 칸 재시도, M2, 폐기 점검, 안전장치 g2). 측정한 구성을 그대로 옮긴다 |
| `routing/` | 자동 등록 / 검토 큐 결정. 9단계 판정이 미채택이면 전부 검토 큐로 보낸다 |
| `flow/` | 상태 흐름 — 접수 → 트리아지 중 → 검토 대기 또는 자동 등록 → 등록 완료 / 폐기 / 실패 |
| `bts/` | BTS 어댑터 — `jira`, `redmine` |
| `store/` | SQLite(표준 라이브러리). 사람이 고친 내역도 저장한다 |
| `web/` | FastAPI 라우트 + Jinja2 템플릿 + HTMX |
| `eval/` | 회귀 게이트. 파이프라인을 바꿀 때 CI에서 품질 하락을 막는다 |

Python 패키지 이름은 영어로 둔다(한글 import 경로는 도구 호환성 문제가 있다). 폴더 한글화는 `docs/`·`report/`·`data/`에 적용한다.

## 3. 화면

화면은 FastAPI가 HTML을 만들어 보내고, 부분 갱신은 HTMX로 처리한다.

선택 이유:
1. Python 하나로 유지보수할 수 있다. 별도 프런트 빌드(Node·TypeScript)가 없어 고장 지점이 적다.
2. 사내 배포 대상이 앱 하나와 Ollama뿐이라 보안 심사 대상이 작다.
3. BTS·디스코드 토큰이 서버 밖으로 나가지 않는다.
4. 표·차트·필터·상태 변경 수준의 화면은 서버 렌더링으로 충분하다.
5. API 타입을 `contracts.py`로 고정해 두므로, 필요하면 프런트(Next.js 등)만 새로 얹을 수 있다.

| 화면 | 내용 |
|---|---|
| 작업 페이지 | 링크 입력 → 진행 상태 → 트리아지 8칸 확인·수정 → 승인 시 BTS 등록 → 티켓 링크 |
| 대시보드 | 상태별 건수, 일자별 유입, 모듈·우선순위 분포, 자동 처리율, 사람 수정 비율, 처리 시간 p95 |

## 4. 안전장치

| 위험 | 대응 |
|---|---|
| 토큰 유출 | BTS·디스코드 토큰은 환경 변수로만 받고 로그·화면에 남기지 않는다 |
| 임의 주소 요청(SSRF) | 설정에 등록한 도메인의 링크만 가져온다 |
| 프롬프트 인젝션 | 리포트 본문은 지시가 아니라 입력 데이터로만 다룬다. 출력은 형식 계약과 안전장치를 통과해야 한다 |
| 개인정보 | 로그·대시보드에서 작성자 식별 정보를 가린다 |
| 수집 제약 | 커뮤니티 수집 전 이용약관·robots를 확인한다. 디스코드는 회사 봇이 설치된 서버만 읽는다. 가져오기에 실패하면 본문 붙여넣기로 넘어간다 |
| 실패 은폐 | 가져오기·트리아지·등록 실패는 `실패` 상태로 남기고 대체 데이터를 만들지 않는다 |

## 5. 진행 순서

1. v1.5 9단계 마무리 — 날조 확인 → 판정 → 결과 보고서 → 태그 `v1.5-archive` → 코드 정리 A단계 브랜치 병합
2. 회귀 게이트를 단독 코드로 정리하고, 저장된 기준선으로 판정이 같은지 확인한 뒤 v1.3·v1.4 게이트·방법 비교·모델 선택·재채점 코드를 지운다
3. 뼈대 — 붙여넣기 출처 → 트리아지 → 검토 큐 → 가짜 BTS까지 한 건이 끝까지 도는 최소 구성과 작업 페이지
4. Jira·Redmine 어댑터
5. 디스코드·게시판 어댑터
6. 대시보드 지표
7. 문서·데이터 폴더 한글화

각 단계는 시작 전에 범위를 확정한다.

## 7. QA 실무 경험과 부트캠프 학습의 활용

- **QA 실무**: 라이브 서비스 QA에서 리포트는 게시판·디스코드·커뮤니티로 들어와 사람이 BTS로 옮겨 적는다. 이 옮겨 적기와 1차 분류를 자동화하되, 등록 직전에 사람이 확인하는 지점(검토 큐)을 남긴 것은 오등록 비용이 크다는 실무 판단이다. BTS가 회사마다 다르다는 경험이 어댑터 구조의 근거다.
- **부트캠프 Private LLM 트랙**:
  - FastAPI·Pydantic 계약 설계는 데이터 파이프라인·FastAPI 과목에서 배웠다.
  - 신뢰 경계·개인정보 가리기·출력 검증은 LLMOps 4장에서 배웠다.
  - 운영 지표(p95·오류율·분모 표기)는 LLMOps 3장에서 배웠다.
  - 입력 정리 순서와 토큰 예산은 컨텍스트 엔지니어링에서 배웠다.
  - 수집 전 리스크 점검은 데이터 수집 과목에서 배웠다.
  - 영역별 계약(`contracts.py`)과 설정 한 곳(`config.py`)은 3차 팀 프로젝트의 구조를 따랐다.
