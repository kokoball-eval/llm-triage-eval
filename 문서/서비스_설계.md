# 서비스 설계 — 링크 접수부터 BTS 등록까지

상태: S1(뼈대)·S2(Jira Cloud·Redmine 연결)·S3(링크 가져오기)·S4(대시보드)·S5-1(생성 시 자동 배정)·S5-2(BTS 상태 동기화와 QA 보드)·S5-3(QA 동작)·S5-4a(동기화 차이 줄이기)·S5-4b(마일스톤 성과)·S5-4c(대시보드 QA 지표)·S5-4d(화면을 열 때 자동 동기화와 BTS 연결 표시)·S5-5a(팀 = BTS 그룹, 담당 = 구성원)·S5-5b("내 담당" 화면) 구현, S5-5c 계획

## 1. 목표

평가 체계로 검증한 트리아지 파이프라인을 사내에서 쓸 수 있는 서비스로 만든다.

- **작업 페이지**: 리포트 링크를 붙여 넣으면 본문을 가져와 트리아지하고, 사람이 확인·수정한 뒤 BTS에 등록한다.
- **대시보드**: 이슈 처리 현황과 운영 지표를 보여 준다.

설계 요구는 하나다. **들어오는 곳(출처)과 나가는 곳(BTS)을 코드 한 파일 단위로 바꿔 끼울 수 있어야 한다.** 회사마다 쓰는 BTS(Jira, Redmine, 사내 도구)와 리포트가 올라오는 곳(공식 홈페이지 게시판, 디스코드, 커뮤니티)이 다르기 때문이다.

| 구분 | 지원 대상 |
|---|---|
| 출처 (링크) | 공식 홈페이지 게시판, 디스코드, 커뮤니티 사이트, Jira, Redmine, 본문 붙여넣기 |
| BTS (등록 대상) | Jira, Redmine |

## 2. 구조 — 가운데는 고정, 바깥은 어댑터

```
[링크] → 접수 ─ 출처 어댑터 ─→ Report ─→ 트리아지 ─→ 라우팅 ─→ 흐름 ─→ BTS 어댑터 → Jira / Redmine
                                                                    ↓
                                                         대시보드 (처리 현황·운영 지표)
```

트리아지·라우팅·흐름은 공통 타입(`Report`, `Issue`)만 다루고 출처나 BTS의 종류를 모른다. 출처·BTS의 차이는 어댑터 안에서 끝난다.

서비스 코드는 패키지 `src/triage_service/`에 있다. 평가 패키지(`src/triage_eval/`)에 8칸 출력 형식용 `contracts.py`가 이미 있어 서비스를 따로 두었고, 둘은 같은 트리아지 함수(`triage_eval.triage.pipeline.triage`)를 쓴다.

### 계약 (`triage_service/contracts.py`)

| 계약 | 함수 | 의미 |
|---|---|---|
| `Source` | `matches(url) -> bool` | 이 링크를 이 어댑터가 처리하는가 |
| | `fetch(url) -> Report` | 제목·본문·작성 시각·원문 링크를 가져온다 |
| `Tracker` | `create(issue) -> Ticket` | BTS에 등록하고 티켓 번호·링크를 돌려준다. `issue.team`이 있으면 그 팀의 계정을 담당자로 넣는다 |
| | `status(key) -> str` | BTS에서의 처리 상태를 조회한다 |
| | `check_assignees() -> list[str]` | 자동 배정 계정이 BTS에서 담당자가 될 수 있는지 확인한다(연결 확인 `--check`) |
| | `snapshot(keys) -> dict[str, BtsState]` | 티켓 여러 건의 BTS 상태·담당자·마지막 변경 시각을 한 번에 읽는다(BTS에 없는 키는 빠진다) |
| | `update(key, status, team, comment)` | 티켓의 상태·담당 팀·코멘트를 바꾼다(빈 값은 그대로). 무엇을 언제 쓸지는 `qa.py`가 정한다 |
| | `versions() -> list[Milestone]` | 프로젝트의 버전(마일스톤) 목록 — 이름·출시일·출시 여부 |
| | `milestone_tickets(name) -> list[BtsTicket]` | 그 버전의 BTS 티켓 전체(서비스가 등록하지 않은 것 포함, `config.MILESTONE_LIMIT`까지) |
| | `check_statuses() -> list[str]` | BTS 워크플로에 다섯 상태(QA Review·In Dev·Resolve·Check·Closed)가 있는지 확인한다(연결 확인 `--check`) |

- 새 출처·새 BTS는 계약을 구현한 파일 하나를 추가하고 목록(출처) 또는 설정(BTS)에 등록하면 붙는다.
- 우선순위·모듈 같은 값의 BTS 필드 매핑(예: Critical → Jira `Highest`, 결제·재화 → 컴포넌트 `Payment`)은 코드가 아니라 설정 파일에 둔다. 회사마다 다른 필드 이름은 설정으로 맞춘다.
- 모든 어댑터는 같은 계약 시험을 통과해야 한다. 시험은 녹화한 API 응답으로 돌려 실제 서버 없이 CI에서 실행한다.

### 영역 (관심사 분리)

| 영역 | 책임 |
|---|---|
| 영역 (`triage_service/`) | 책임 | 상태 |
|---|---|---|
| `contracts.py` | 영역 사이에 주고받는 타입 — `Report`, `Issue`, `Ticket`, 계약 `Source`·`Tracker` | S1 |
| `config.py` | 서비스 설정 한 곳 — DB 위치, 사용할 BTS, 접속 주소, 입력 길이 상한. 모델·생성 옵션은 평가 패키지 설정을 따른다 | S1 |
| `intake/` | 출처 어댑터 — `paste`(붙여넣기), `bts.py`(Jira·Redmine 이슈 링크 → QA 이슈), `board.py`(게시판 글, 사이트별 CSS 선택자는 `설정/출처.toml`), `discord.py`(봇 API), `fetching.py`(허용한 곳만·리다이렉트 안 따라감·크기 상한), `settings.py`(출처 설정 검사), `reception.py`(미리보기·접수 확인: 같은 원문 한 번만, 숨은 칸 검증) | S3 |
| `worker.py` | 작업자 하나가 차례대로 채택 파이프라인(`triage_eval.triage.pipeline.triage`)을 호출. 측정한 구성을 고치지 않는다 | S1 |
| `routing.py` | 자동 등록 / 검토 결정. 9단계 판정 미채택이라 전부 검토로 보낸다 | S1 |
| `flow.py` | 상태 흐름 — 접수 → 트리아지 중 → 검토 대기 → 등록 완료 / 폐기, 처리 중(접수·트리아지 중·검토 대기) → 실패 → 접수(다시 시도) | S1 |
| `review.py` | 사람이 확인·수정한 8칸을 형식 규칙(R1~R7)으로 검사하고 등록·폐기 | S1 |
| `assign.py` | 생성 시 자동 배정 — 확정 8칸의 [처리]가 받을 쪽(QA·개발·CS)을, [모듈]이 개발팀을 정한다. 팀 이름과 모듈 → 팀 표는 `설정/bts_매핑.toml [assign]` | S5-1 |
| `sync.py` | BTS 상태 동기화와 QA 보드 — 등록한 티켓의 상태를 읽어 저장하고, 재현 대기(QA Review)·회귀 테스트 대기(Resolve)·보류(Check)·팀별 미해결로 묶는다 | S5-2·S5-3 |
| `qa.py` | QA 동작 — 재현 확인·회귀 테스트 통과·실패·보류·코멘트를 BTS에 쓴다. 쓰기 직전에 상태를 다시 읽고, 쓴 뒤 다시 읽어 확인하고, 모두 기록한다 | S5-3 |
| `bts/` | BTS 어댑터 — `fake`(같은 DB에 저장), `jira`(Jira Cloud REST v3), `redmine`(REST JSON). 접속 클라이언트는 `clients.py` 한 곳(등록과 이슈 가져오기가 함께 씀). `settings.py`가 `설정/bts_매핑.toml`과 토큰을 시작 시점에 검사 | S2 |
| `store.py` | SQLite(표준 라이브러리). 모델이 낸 8칸·사람이 확정한 8칸·고친 칸·처리 구성 지문, 상태 변경 이력(transitions)을 함께 저장한다 | S1·S4 |
| `metrics.py` | 대시보드 지표 계산 — 비율은 분자·분모를 함께, 처리 시간은 상태 이력으로, 백분위는 nearest-rank | S4 |
| `web/` | FastAPI 라우트 + Jinja2 템플릿. 업무 규칙 없이 각 영역의 결과를 보여 주기만 한다 | S1 |
| `cli.py` | 실행 명령 `uv run triage-serve [--check]` — 설정·토큰 검사 후 서버 시작 | S1 |

회귀 게이트·성능표는 평가 패키지(`triage_eval/evaluation/`)에 있고, 파이프라인을 바꿀 때 품질 하락을 막는다.

Python 패키지 이름은 영어로 둔다(한글 import 경로는 도구 호환성 문제가 있다). 폴더 한글화는 `기준/`·`데이터/`·`문서/`·`보고서/`에 적용했다.

## 3. 화면

화면은 FastAPI가 HTML을 만들어 보낸다. 작업 페이지는 트리아지가 끝날 때까지 화면 전체를 다시 읽는 것(meta refresh)으로 충분했고, 대시보드도 기간을 바꾸면 페이지를 다시 읽는 방식으로 충분해 HTMX는 넣지 않았다(S4에서 판단). 막대 그래프는 서버가 HTML·CSS로 그려 차트 라이브러리나 외부 CDN 없이 사내망에서 그대로 동작한다. 화면의 일부만 자주 바뀌어야 하는 기능이 생기면 그때 붙인다.

선택 이유:
1. Python 하나로 유지보수할 수 있다. 별도 프런트 빌드(Node·TypeScript)가 없어 고장 지점이 적다.
2. 사내 배포 대상이 앱 하나와 Ollama뿐이라 보안 심사 대상이 작다.
3. BTS·디스코드 토큰이 서버 밖으로 나가지 않는다.
4. 표·차트·필터·상태 변경 수준의 화면은 서버 렌더링으로 충분하다.
5. API 타입을 `contracts.py`로 고정해 두므로, 필요하면 프런트(Next.js 등)만 새로 얹을 수 있다.

| 화면 | 내용 |
|---|---|
| 작업 페이지 | 링크 입력 → 진행 상태 → 트리아지 8칸 확인·수정 → 승인 시 BTS 등록 → 티켓 링크 |
| 대시보드 | 상태별 건수, 일자별 유입, 모듈·우선순위 분포, 자동 처리율, 사람 수정 비율, 처리 시간 p95 |

## 4. 안전장치

| 위험 | 대응 |
|---|---|
| 토큰 유출 | BTS·디스코드 토큰은 환경 변수로만 받고 로그·화면에 남기지 않는다 |
| 임의 주소 요청(SSRF) | 설정에 등록한 도메인의 링크만 가져온다 |
| 프롬프트 인젝션 | 리포트 본문은 지시가 아니라 입력 데이터로만 다룬다. 출력은 형식 계약과 안전장치를 통과해야 한다 |
| 개인정보 | 로그·대시보드에서 작성자 식별 정보를 가린다 |
| 수집 제약 | 커뮤니티 수집 전 이용약관·robots를 확인한다. 디스코드는 회사 봇이 설치된 서버만 읽는다. 가져오기에 실패하면 본문 붙여넣기로 넘어간다 |
| 실패 은폐 | 가져오기·트리아지·등록 실패는 `실패` 상태로 남기고 대체 데이터를 만들지 않는다 |
| 측정과 다른 입력 | 서비스 입력은 평가셋 문항과 같은 모양으로 만들고(시험으로 고정), QA 이슈의 작성자는 평가셋에 쓰인 값만 받는다(안전장치 규칙이 작성자 값을 본다) |
| 외부 접속·요청 위조 | S1은 127.0.0.1에서만 접속을 받는다. 실제 BTS 토큰을 쓰는 S2 전에 요청 위조 방지(CSRF 토큰)와 Host 확인을 넣는다 |

## 5. 진행 순서

v1.5 마무리, 회귀 게이트 정리, 문서·데이터 폴더 한글화는 끝났다(태그 `v1.5-archive`, CHANGELOG 코드 정리 A·B단계).

| 단계 | 내용 | 상태 |
|---|---|---|
| S1 | 뼈대 — 붙여넣기 출처 → 트리아지 → 검토 대기 → 사람 확인·수정 → 가짜 BTS 등록, 작업 페이지 | 구현 |
| S2 | Jira·Redmine 어댑터, 필드 매핑 설정 파일, 요청 위조 방지(Origin·Host 확인), BTS 등록 실패 건을 검토로 되돌리기, 서비스 표식으로 중복 등록 방지 | 구현 — 실제 Jira Cloud·Redmine 6.0(로컬 Docker)에 등록 확인 |
| S3 | 링크 가져오기 — Jira·Redmine 이슈, 게시판 글, 디스코드 메시지. 미리보기 후 접수, 같은 링크 한 번만 접수, 허용한 곳만 요청 | 구현 — 실제 Jira·Redmine 이슈와 로컬 견본 게시판으로 확인, 디스코드는 문서 형식 응답으로만 시험 |
| S4 | 대시보드 — 상태별 건수, 일자별 유입(출처별), 확정 8칸 분포, 사람 수정 비율(칸별·Critical 올림/내림), 자동 처리율, 처리 시간 p50·p95, 실패 | 구현 — HTMX 없이 서버 렌더링 막대 |
| S5-1 | 생성 시 자동 배정 — 재현이 필요하면 QA팀, 개발로 넘기면 모듈의 팀(클라·서버·아트·기획 등). 검토 화면에서 바꿀 수 있고 규칙의 팀과 함께 저장 | 구현 — 실제 Jira에 담당자를 넣어 등록 확인(KAN-8) |
| S5-2 | BTS 상태 동기화와 QA 검증 대기 목록(읽기만) — 설정한 범위의 티켓 상태·담당자를 가져와 검증 대기·재현 대기·팀별 미해결을 보여 준다 | 구현 — 실제 Jira KAN에서 상태 읽기 확인 |
| S5-3 | QA 동작(BTS에 쓰기) — BTS 상태를 다섯 단계로 통일하고, 재현 확인(In Dev·모듈 팀), 회귀 테스트 통과(Closed)·실패(In Dev), 보류(Check), 코멘트. 보내기 직전에 상태를 다시 읽는다. 새 티켓의 첫 상태도 [처리]로 정한다 | 구현 — 실제 Jira KAN(KAN-8)·Redmine 6.0(로컬 Docker)에 동작 순서를 모두 보내 확인 |
| S5-4a | Jira·Redmine 동기화 차이 줄이기 — Jira 검색에 reconcileIssues(방금 바뀐 이슈도 최신 값), Redmine 팀 = 일감 범주·모듈 = 사용자 정의 필드(Jira 라벨과 같은 구실) | 구현 — 실제 Jira KAN·Redmine에서 확인 |
| S5-4b | 마일스톤 성과(첫 화면) — 마일스톤 = BTS 버전(Jira 릴리스·Redmine 목표 버전). 검토 화면에서 마일스톤을 고르고, 마일스톤의 BTS 티켓 전체를 읽어 Closed 수·완료율·남은 건수·재오픈 수·QA가 회귀 통과로 닫은 수를 보인다 | 구현 — 실제 Jira KAN(KAN-9)·Redmine(#3)에 마일스톤 0.0.1로 등록하고 읽어 확인 |
| S5-4c | 대시보드 QA 지표 — 회귀 테스트 대기 건수·시간, 재오픈률, 팀별 미해결, 배정 팀을 사람이 바꾼 비율(마일스톤별) | 구현 — 실제 Jira KAN 마일스톤 검색에서 팀 라벨 읽기 확인 |

### S2에서 확인한 것

- **계약 시험은 실제 응답으로 돈다.** 실제 Jira Cloud와 Redmine에 등록·표식 검색·상태 조회·거절을 한 번씩 보내 응답을 녹화했고(`tests/bts_responses/`, 인증 정보 없음, Jira 사이트 주소는 `your-site`로 바꿈), CI는 이 녹화로 세 어댑터(가짜·Jira·Redmine)를 같은 계약 시험으로 검사한다.
- **Jira 프로젝트 유형에 따라 이슈 유형 이름이 다르다.** Jira 무료 사이트의 시작 화면으로 만든 공간은 팀 관리형이었고 "Bug" 유형이 없었다(에픽·작업·스토리·하위 작업). 서비스는 이슈 유형 이름을 설정 파일에서 받으므로, 이 공간에는 `issue_type = "작업"`으로 등록했다. 우선순위(Highest~Lowest)와 라벨은 그대로 쓸 수 있었다.
- **Redmine 기본 데이터는 언어에 따라 이름이 다르다.** 영문 기본 데이터의 유형 1은 Bug, 우선순위 1~5는 Low~Immediate다. 서비스는 번호로 대응하므로 이름과 관계없이 동작한다.
- **표식 검색은 정확히 같은 것만 인정한다.** Redmine 설명 검색(`~`)은 포함 검색이라 `triage-x-1`로 찾으면 `triage-x-12`도 걸린다(독립 검토에서 발견). 돌려받은 티켓의 표식 줄을 정확히 비교하도록 고쳤다. Jira 라벨 검색은 전체 일치라 해당하지 않지만, 등록 직후 검색 색인이 늦게 반영될 수 있어 끊긴 직후 재등록은 Jira에서 먼저 확인하는 것으로 안내한다.
- **토큰은 `.env`에만 있다.** 연결 확인(`triage-serve --check`)과 녹화 과정에서 토큰을 화면이나 파일에 출력하지 않았다.

### S3에서 확인한 것

- **가져온 내용은 미리보기를 거친다.** 링크로 가져온 제목·본문은 새 리포트 입력 칸에 채워 보여 주고, 사람이 [트리아지]를 눌러야 접수된다. 게시판 구조가 바뀌어 엉뚱한 글을 가져오는 경우를 사람이 걸러 내기 위해서다. 길이 상한(제목 100자·본문 1,000자)도 붙여넣기와 같다.
- **허용한 곳만 부른다.** 링크는 설정에 적힌 호스트·경로와 맞을 때만 요청한다. 시험에서 설정 밖 호스트, 메타데이터 주소(169.254.169.254), 비슷한 이름의 위장 호스트, `file://`가 요청 없이 거절되고, 리다이렉트를 따라가지 않으며, 응답 크기 상한에서 멈추는 것을 확인했다.
- **BTS 이슈를 다시 트리아지할 수 있다.** Jira·Redmine 이슈 링크는 측정 때의 입력 종류 B(QA 이슈)로 들어간다. 실제 Jira KAN-5와 Redmine #2를 링크로 가져왔다. 다만 이 서비스가 등록한 이슈는 설명에 8칸이 들어 있어, 다시 가져오면 이전 판정이 본문에 포함된다. QA가 직접 쓴 이슈를 점검하는 용도로 쓴다.
- **게시판은 로컬 견본으로 확인했다.** 실제 외부 커뮤니티는 이용 약관·robots 확인이 필요해 이번 범위에서 뺐다. 로컬 견본 게시판(127.0.0.1:8765)의 글을 링크로 가져와 트리아지하고 실제 Jira에 등록(KAN-6)했고, 같은 링크를 다시 넣으면 기존 리포트로 안내되는 것을 확인했다.
- **같은 원문은 링크 모양이 달라도 한 번만 접수한다.** 끝의 `/`, 쿼리, 대문자, 디스코드 하위 도메인만 다른 링크를 하나로 맞춰 확인한다(독립 검토에서 발견). 폐기·실패한 리포트의 링크도 다시 접수하지 않고 기존 리포트로 안내한다.
- **시각은 현지 시각으로 맞춘다.** 디스코드는 UTC, 게시판은 시간대가 붙은 값으로 오므로 이 PC의 현지 시각으로 바꿔 `[게시 일시]`에 넣는다. 측정한 입력의 게시 일시가 현지 시각이었기 때문이다.
- **한계** — 받는 시간 제한은 읽기 한 번마다 걸리고 전체 시간 상한은 없다. 허용한 곳만 부르는 로컬 도구라 기록만 한다.
- **디스코드는 실제 봇 연결 전이다.** 코드와 시험(공식 문서 형식의 응답)까지 만들었고, 회사 봇 토큰(`DISCORD_BOT_TOKEN`)이 있어야 켜진다.

### S4에서 확인한 것

- **비율에는 분모를 함께 쓴다.** 등록 3건 중 1건 수정을 "33.3%"로만 쓰면 표본 크기를 알 수 없어, 모든 비율을 "33.3% (1 / 3건)"처럼 보이고 분모가 0이면 "데이터 없음"을 보인다.
- **처리 시간은 상태 이력으로 센다.** 상태가 바뀔 때마다 같은 트랜잭션 안에서 이력을 남기도록 저장소를 바꿨다(허용되지 않은 전이는 이력도 남기지 않음). 검토 대기 시간은 리포트 한 건 기준이고, 검토로 되돌아가 여러 번 머문 건은 합친다. 지금 검토 대기 중인 건과 이력 표가 생기기 전에 접수한 리포트는 시간 지표에서 빠지므로 그 건수를 화면에 함께 적는다(오래 쌓인 건이 p95 에서 안 보이는 착시 방지).
- **사람 수정은 운영 중의 품질 신호다.** 실제 모델로 친구 목록 표시 오류 리포트를 트리아지했을 때 모델은 "버그 아님 / Trivial"로 판정했고, 검토에서 "결함 / Minor"로 고쳐 등록(KAN-7)하자 대시보드의 분류·우선순위 수정 비율에 바로 반영됐다. Critical로 올린 건은 측정의 X-1(Critical 미상신)이 운영에서도 나오는지 보는 지표로 따로 센다.
- **휴대폰 폭에서도 읽힌다.** 375px 폭에서 가로 스크롤 없이 상태 칸이 두 줄로 접힌다.

### S5 계획 — BTS를 원본으로 두고 QA 업무를 서비스 안에서

QA가 Jira·Redmine을 따로 열지 않고 등록 → 배정 → 재현 → 검증 → 종료를 서비스 안에서 처리하게 한다. BTS를 대체하지 않는다. 개발자는 계속 BTS에서 일하므로 서비스가 자체 이슈 목록을 가지면 같은 버그의 상태가 두 곳에서 달라진다. 서비스는 BTS를 읽어 오고, QA가 하는 동작만 BTS API로 다시 써 넣는다. BTS가 서비스로 변경을 알려 주는 방식(웹훅)은 서비스가 이 PC(127.0.0.1)에서만 열려 있어 쓰지 않는다. 담당자 지정 화면, 스프린트·보드처럼 개발 쪽 일은 BTS에 둔다. 각 하위 단계는 브랜치 하나·독립 검토·병합으로 끝낸다.

### S5-5a에서 확인한 것

- **팀 = BTS 그룹, 담당 = 구성원 한 사람(2026-11-25 경민 결정).** 설정의 팀 대응을 계정 하나에서 그룹으로 바꿨다(`[jira.teams]` 그룹 이름, `[redmine.teams]` 그룹 번호). 팀장은 `[<bts>.leads]`에 적고 QA팀장은 필수다. 등록할 때 그룹 구성원을 BTS에서 읽고, 구성원마다 이 프로젝트에서 맡은 미해결(Closed 아님) 이슈 수를 BTS에 물어 가장 적은 사람에게 배정한다(같으면 서비스가 가장 오래전에 배정한 사람). Jira는 그룹을 담당자로 둘 수 없어서, Redmine은 Jira와 같게 하려고 둘 다 사람에게 배정한다.
- **팀장의 역할은 판정 기준서로 정했다.** 기준서 §0 "Critical은 리드 QA 사인을 거친다"에 따라 `[처리] 긴급 사인 요청`은 QA팀장이 받는다(QA Review). 팀장이 상세 화면의 [사인 후 개발 전달]을 누르면 In Dev와 함께 개발팀 그룹 구성원 중 미해결이 가장 적은 사람에게 넘어간다. 누르는 사람이 QA팀장인지는 BTS 토큰 주인(Jira `/myself`, Redmine `/users/current`)으로 확인한다. 나머지 [처리]는 팀장도 구성원의 한 사람으로 자동 분배한다 — 모든 이슈에 팀장이 나누는 단계를 두면 사람 병목이 늘고, 기준서가 사람 서명을 Critical에만 둔 것과도 맞지 않는다. S5-4까지 긴급 사인 요청을 개발팀으로 바로 보내던 것은 기준서와 어긋난 결함이라 고쳤다([ISSUE-015](결함_기록.md#issue-015)). 검토 화면에서 사람이 다른 팀을 골라도 긴급 사인 요청은 QA팀장에게 간다(독립 검토에서 발견 — 팀을 바꾸면 사인할 팀장이 흐름에서 빠졌다). 자동 배정을 쓰지 않으면 팀장도 없으므로 예전처럼 재현 확인으로 넘긴다.
- **QA 담당을 기억한다.** QA팀으로 간 이슈는 처음 배정된 사람을 배정 기록의 `qa_owner`로 남긴다. 이슈가 개발로 넘어가 BTS 담당자가 바뀌어도 그대로라, Resolve가 되면 그 사람의 회귀 테스트 차례가 된다(S5-5b에서 화면에 쓴다).
- **검토 화면.** 배정 팀 아래에 그 팀 구성원과 각자의 미해결 수, 규칙이 고른 사람을 보이고 다른 구성원을 고를 수 있다. BTS를 부르므로 검토 대기 건을 열 때만 읽고, 읽지 못해도 화면은 열며 등록할 때 다시 읽는다.
- **실제 BTS.** Jira에 그룹 6개(QA팀 = 경민·수락한 계정, 개발 5팀 = 수락한 계정)를 만들고, Redmine에 사용자 QA 팀원·운영~기획 팀장과 그룹 6개를 만들어 프로젝트 구성원으로 넣었다(관리자 계정 이름을 QA 팀장으로 바꿈). 두 BTS에서 긴급 사인 요청 1건(팀장 → 사인 → 개발팀 구성원)과 재현 대기 2건(QA 구성원 중 미해결이 적은 사람)을 등록해 확인하고, 그룹 구성원·미해결 수·토큰 주인 응답을 녹화해 CI 계약 시험에 넣었다. `--check`가 그룹 구성원, 구성원이 담당자가 될 수 있는지, 팀장이 그룹 구성원인지를 확인한다.
- **Jira 미해결 수는 지연 없이 센다.** 처음에는 approximate-count를 썼는데 검색 색인이라 방금 등록한 이슈가 몇 초 늦게 세어져, 연달아 등록한 KAN-11·12가 같은 사람에게 갔다. approximate-count는 최근 이슈를 최신 값으로 읽는 `reconcileIssues`를 받지 않아, 검색(`/search/jql`, fields=id)을 끝까지 세고 최근에 다룬 이슈 ID를 함께 보내는 방식으로 바꿨다. 바꾼 뒤 재현 대기 3건을 연달아 등록하자 두 BTS 모두 두 사람에게 번갈아 갔다(Jira KAN-13~15, Redmine #7~9). 사람이 팀을 "클라"로 골라도 긴급 사인 요청이 QA팀장에게 가는 것도 확인했다(KAN-16, #10).
- **한계** — "최근 배정"은 서비스 등록 기록만 보고 사인·재현 확인으로 넘긴 것은 세지 않는다. 그룹 구성원 읽기에는 Jira "사용자 및 그룹 찾아보기" 권한, Redmine 관리자 API 키가 필요하다. 등록할 때 구성원 수만큼 BTS 요청이 늘어난다.

### S5-4d에서 확인한 것

- **화면을 열 때 뒤에서 읽는다(2026-11-25 경민 결정).** 첫 화면·QA 보드·대시보드를 열 때 마지막 동기화(실패 포함)가 10분(`config.AUTO_SYNC_MINUTES`)보다 오래됐으면 동기화를 뒤에서 시작하고, 화면은 읽어 둔 값으로 바로 연다. 도는 동안은 화면이 1초마다 다시 읽혀 끝난 값이 보인다. BTS가 느리거나 멈춰도 화면이 묶이지 않고, 실패해도 10분 뒤에 다시 시도하므로 BTS가 멈춘 동안 화면을 열 때마다 부르지 않는다. S5-2의 "화면을 여는 것만으로는 BTS를 부르지 않는다"는 이것으로 바뀌었다. [지금 동기화] 버튼은 그대로 둔다.
- **동기화는 한 번에 하나.** 잠금 하나로 자동 동기화와 버튼이 겹치지 않는다. 버튼은 도는 동기화가 끝난 뒤 다시 읽는다. S5-2의 한계(연달아 누른 두 동기화 중 늦게 끝난 쪽이 오래된 값을 덮어씀)도 이것으로 막혔다. 등록과 QA 동작도 같은 잠금 안에서 한다. 동기화가 먼저 읽어 둔 옛 상태를 QA 동작이 쓴 새 상태 뒤에 저장해 화면과 상태 변화 기록을 되돌리는 경합을 독립 검토에서 찾아 막았다(동기화가 도는 중이면 QA 동작은 끝날 때까지 기다린다).
- **BTS 연결 표시.** 모든 화면 머리 오른쪽에 "● Jira 연결됨 · 3분 전"처럼 보인다. 표시하려고 BTS를 따로 부르지 않고 마지막 동기화 결과로 정한다: 다 읽음(연결됨, 초록), 일부 실패(노랑), 아무것도 읽지 못함(연결 안 됨, 빨강), 읽는 중(노랑), 서버를 켠 뒤 아직 읽지 않음(확인 전). 마우스를 올리면 실패 이유가, 누르면 마지막 동기화 결과가 있는 QA 화면이 나온다. 와이파이 아이콘처럼 "연결돼 있다"만 보이는 대신 언제 읽은 값인지를 함께 보여, 화면의 숫자를 얼마나 믿을지 판단할 수 있게 했다.
- **한계** — 마지막 동기화 시각은 서버 메모리에만 있어 서버를 다시 켜면 처음 여는 화면에서 다시 읽는다. 연결 표시는 마지막 동기화 시점의 상태라 그 뒤에 BTS가 끊긴 것은 다음 동기화(최대 10분 뒤, 또는 버튼) 전까지 모른다. 등록·QA 동작이 실패하면 그 화면에서 따로 알린다.

### S5-4c에서 확인한 것

- **QA 지표는 마일스톤 단위다.** 대시보드에 "QA 지표 (마일스톤별)" 칸을 두고 마일스톤을 고른다(기본값 현재 마일스톤). 기존 지표의 기간 필터와는 따로 움직이고, 한쪽을 바꿔도 다른 쪽 값이 주소에 남는다. 화면을 열어도 BTS를 부르지 않는다.
- **팀은 BTS의 팀 표식에서 읽는다.** 마일스톤 티켓을 읽을 때 Jira는 `팀_<이름>` 라벨, Redmine은 일감 범주 이름을 팀으로 둔다. 서비스가 등록할 때 붙이는 표식과 같아서, 서비스로 등록하지 않은 티켓도 BTS에서 같은 표식만 붙이면 팀별 미해결에 들어간다. 표식이 없으면 "팀 없음"이다. Jira 마일스톤 검색에 `labels` 필드를 더해 실제 KAN에서 다시 녹화했다(KAN-9 → QA). Redmine 목록 응답에는 범주가 이미 들어 있어 요청이 늘지 않는다.
- **지표 정의.** 회귀 테스트 대기 = 지금 Resolve인 건수와 가장 오래 기다린 시간, Resolve에 머문 시간(중앙값·p95). 재오픈률 = Resolve → In Dev를 본 티켓 ÷ Resolve에 있는 것을 본 티켓. 사람이 바꾼 배정 = 서비스로 등록하고 자동 배정을 쓴 티켓 중 규칙의 팀과 확정 팀이 다른 비율(이미 있던 티켓에 연결한 건, 재현 확인 뒤 팀을 옮긴 것은 세지 않는다). 모든 비율에 분자·분모를 함께 보인다.
- **한계** — 상태 변화 시각은 [지금 동기화]로 발견한 시각이라 동기화 간격만큼 오차가 있다(S5-4d에서 화면을 열 때 자동 동기화로 줄인다). 처음 읽었을 때 이미 Resolve였던 티켓은 대기 시간에서 빼고 건수를 적는다. 사람이 바꾼 배정은 BTS에 직접 만든 티켓에는 규칙의 팀이 없어 셀 수 없다.

### S5-4b에서 확인한 것

- **마일스톤 = BTS 버전.** Jira 릴리스(`fixVersions`)와 Redmine 목표 버전(`fixed_version`)이 두 BTS에 공통으로 있는 단위다. 두 BTS에 같은 이름·출시일로 0.0.1(2027-01-13)·0.1.0(2027-03-10)·0.2.0(2027-05-12, 부트캠프 수료일)을 API로 만들었다(약 2달 간격, 마일스톤이 바뀌면 둘째 자리를 올린다). Jira 팀 관리형 공간은 기능 설정에 릴리스 스위치가 없고, 스페이스 상단 보기(+)에서 "릴리스"를 추가해야 티켓에 버전 칸이 생겼다(2026-11-24).
- **성과는 BTS 티켓 전체로 센다.** QA 성과는 마일스톤 단위로 몇 건을 Closed 했는가라서, 서비스가 등록한 티켓만이 아니라 그 버전의 BTS 티켓 전체(BTS에 직접 등록한 이슈 포함)를 [지금 동기화] 때 읽어 `bts_tickets`에 둔다. 출시 전 버전만 읽고, 출시한 버전은 마지막에 읽은 값을 보인다. 첫 화면 맨 위 카드: Closed 수·완료율, QA가 서비스에서 회귀 통과로 닫은 수, 재오픈(Resolve → In Dev를 본 티켓) 수, 남은 건수(상태별), 출시일까지 남은 날. 첫 화면을 열어도 BTS를 부르지 않는다.
- **검토 화면에서 마일스톤을 고른다.** 마지막 동기화로 읽은 출시 전 버전만 보이고 기본값은 현재 마일스톤(출시 전 중 출시일이 가장 이른 것)이다. 등록할 때 BTS에 넣는다. 목록에 없는 값은 서버가 거절한다(화면 입력은 신뢰 경계).
- **Jira 검색 지연을 실제로 봤다.** KAN-9를 버전 0.0.1로 만든 직후 `fixVersion = "0.0.1"` 검색에 나오지 않았고 몇 초 뒤에 나왔다. 버전을 바꾼 직후 검색에 `reconcileIssues`(그 이슈의 숫자 ID)를 붙이면 바로 보이고 없으면 안 보였다. 그래서 마일스톤 검색에도 최근에 다룬 이슈 ID(최대 50개)를 붙인다. Redmine은 목록 조회가 DB를 바로 읽어 지연이 없었다.
- **한계** — 티켓 하나는 마일스톤 하나로 센다(Jira는 버전을 여러 개 걸 수 있지만 마지막에 읽은 마일스톤에 들어간다). 마일스톤 하나에서 500건을 넘으면 동기화 결과에 경고를 보인다. 상태 변화는 서비스가 발견한 시각이라 동기화 사이에 Resolve → In Dev → Resolve가 오가면 재오픈을 놓친다(QA가 서비스에서 실패 처리한 것은 쓴 즉시 반영). 버전이 없는 BTS 티켓은 읽지 않는다.

### S5-4a에서 확인한 것

두 BTS에서 동기화가 다르게 동작하던 점을 정리하고, 줄일 수 있는 것은 줄였다(2026-11-24).

| 항목 | Jira | Redmine | 결과 |
|---|---|---|---|
| 읽는 시점 | [지금 동기화] 버튼 | 같음 | 같음 |
| 여러 건 읽기 | 검색(`/search/jql`)이 색인이라 방금 바뀐 값이 늦게 보일 수 있음 | 목록 조회가 DB를 바로 읽음 | Jira 검색에 아는 이슈의 숫자 ID를 `reconcileIssues`로 함께 보내 최신 값으로 읽는다. ID는 등록·단건 조회·검색 응답에서 얻어 어댑터가 기억한다 |
| 팀 표시 | 담당자 + `팀_<이름>` 라벨 | 담당자만 | Redmine에 팀 이름과 같은 일감 범주를 만들고 등록·재현 확인 때 넣는다. 범주는 이름으로 찾고, 자동 배정을 쓰면 `--check`가 팀마다 범주가 있는지 확인한다 |
| 모듈 표시 | `모듈_<이름>` 라벨 | 설명에만 | Redmine에 "모듈" 사용자 정의 필드(목록·여러 값)를 만들고 번호를 `module_field_id`에 적으면 넣는다. 없으면 설명에만 남긴다. 필드 번호가 틀리면 Redmine이 조용히 무시하고 필드 정의는 관리자만 읽을 수 있어 `--check`가 확인하지 못한다 |
| 쓰기 | 담당자·상태·코멘트를 따로 보냄(일부만 될 수 있음) | PUT 한 번(워크플로가 막으면 상태만 무시될 수 있음) | API 구조상 같게 만들 수 없어, 둘 다 쓴 뒤 단건 조회로 확인한다(S5-3) |
| 상태 이름 | 한국어 계정에서 Closed가 "종료" | 이름 그대로 | 완료 범주를 Closed로 읽는다(S5-3) |
| 시각 형식 | 밀리초 + 시간대 | 초 단위 UTC | 같은 시각으로 바꿔 계산한다 |

- **실제 확인.** Redmine에 범주 6개(QA·운영·클라·서버·아트·기획)와 "모듈" 필드(1번)를 만들고, 일감 #2를 서버 범주·모듈 두 값으로 등록한 뒤 클라로 재배정해 범주가 바뀌는 것을 확인했다. Jira는 같은 검색에 `reconcileIssues`를 붙여도 정상 응답(200)이었다. 범주 목록 응답은 녹화해 계약 시험에 넣었다.
- **한계** — 숫자 ID는 서버를 다시 켜면 비고, 다음 동기화 검색 결과로 다시 채워진다. `reconcileIssues`가 늦은 값을 실제로 바로잡는 것은 S5-4b에서 확인했다(시험 티켓 KAN-9의 버전을 바꾼 직후 검색: 매개변수가 있으면 바로 보이고 없으면 안 보임).

### S5-3에서 확인한 것

- **BTS 상태를 다섯 단계로 통일했다(2026-11-24 결정).** 서비스와 Jira·Redmine이 같은 이름을 쓴다. 회사마다 이름을 다르게 두는 대응표(S5-2의 `[<bts>.status]`)는 없앴고, 남아 있으면 서버가 "모르는 키"로 멈춘다. `--check`가 BTS 워크플로에 다섯 상태가 있는지 본다.

| 상태 | 뜻 | QA 화면 | 서비스 동작 |
|---|---|---|---|
| QA Review | QA팀이 문제 상황의 재현을 확인하는 중 | 재현 대기 | 재현 확인(코멘트 필수) → In Dev, 담당을 첫 모듈의 팀으로 |
| In Dev | 재현이 끝나 개발팀이 수정·개선하는 중 | 팀별 미해결 | — (개발이 BTS에서 Resolve로) |
| Resolve | 수정이 끝나 QA 회귀 테스트가 필요함 | 회귀 테스트 대기 | 통과 → Closed / 실패(코멘트 필수) → In Dev |
| Check | 일정 지연 등으로 대응을 보류함(사유 코멘트) | 보류 | — |
| Closed | 모든 대응이 끝남 | — | — |

  보류(→ Check, 코멘트 필수)는 QA Review·In Dev·Resolve에서, 코멘트는 Closed가 아니면 언제나 할 수 있다. 재현 확인은 개발팀으로 넘기는 동작이라 [모듈]이 "해당 없음"이면 사람이 팀을 고른다.
- **새 티켓의 첫 상태도 [처리]로 정한다.** 등록(재현 대기)·정보 요청 후 보류는 QA Review, 개발 배정·긴급 사인 요청은 In Dev다. CS 응대는 QA 재현이 필요한 건만 QA Review·QA팀, 아니면 Check·CS팀(예시 설정의 "운영")으로 두고 사유 코멘트를 남긴다. 재현 필요 여부의 기본값은 규칙([분류]가 결함이면 필요)이고 검토 화면에서 바꾼다. 사람 확인이 줄어도 같은 규칙으로 동작하게 하려는 것이다. BTS는 새 티켓을 QA Review로 만들므로 다를 때만 바꾸고, 바꾸지 못해도 티켓은 이미 있어 등록 완료로 두고 실패를 QA 기록에 남긴다.
- **Jira는 "Closed"를 계정 언어로 번역해 돌려준다.** 한국어 계정에서 공용 상태 Closed가 "종료"로 온다(2026-11-24 KAN에서 확인). 한국어 화면을 유지하기 위해, Jira 어댑터는 완료 범주(statusCategory done) 상태를 Closed로 읽고 Closed로 보낼 때도 완료 범주로 가는 전환을 고른다. 그래서 워크플로에 완료 범주 상태는 하나만 둔다(`--check`가 확인). 우선순위도 같은 방식으로 번역되어 화면에는 중요·주요·사소·경미함으로 보이지만, 등록은 영어 이름(Critical 등)으로 된다(KAN-8 우선순위를 바꿔 보고 되돌려 확인).
- **전환 번호는 설정에 두지 않는다.** Jira는 티켓의 전환 목록을 읽어 목표 상태로 가는 전환을 찾는다. 전환 번호는 워크플로마다 다르다. Redmine은 상태 목록에서 이름으로 번호를 찾아 PUT 한 번에 상태·담당자·코멘트를 함께 보낸다.
- **쓰기 직전·직후에 다시 읽는다.** 화면은 마지막 동기화 값을 보여 주므로, 그사이 개발자가 상태를 바꿨으면 쓰지 않고 지금 상태를 저장해 알린다. 상태를 바꾸는 버튼은 두 번 눌러도 두 번째가 여기에 걸린다(코멘트만 하는 동작은 두 번 달린다). BTS 상태를 다시 읽지 못하면 보내지 않는다. 쓴 뒤에는 단건 조회로 다시 읽어 목표 상태가 됐는지 확인한다(Jira 검색은 색인이라 방금 쓴 값이 늦게 보일 수 있다). Jira는 담당자·상태·코멘트를 따로 보내 일부만 될 수 있고, Redmine은 워크플로가 막은 상태 변경을 오류 없이 무시할 수 있어서다. 쓰기 요청이 도중에 실패하면 담당 팀이 바뀌었는지 알 수 없어 BTS에서 확인하라고 알린다. 실패하거나 일부만 된 것도 `qa_actions`에 그대로 남겨 상세 화면에 보인다.
- **재현 확인으로 바꾼 팀은 QA 기록에 둔다.** 등록 때 배정(`assignment`)은 그대로 두어 S5-4의 "사람이 바꾼 비율"이 흐려지지 않게 하고(S5-4c), 보드는 QA 기록의 마지막 팀을 지금 담당 팀으로 센다. Jira는 다른 팀 라벨을 지우고 새 `팀_<이름>` 라벨을 붙인다.
- **실제 확인.** Jira KAN-8과 Redmine 새 일감(#1, 프로젝트 LLM-Triage)에 재현 확인 → (개발 Resolve) → 회귀 실패 → (Resolve) → 통과(Closed) → 보류(Check) → 코멘트 → QA Review로 되돌리기를 순서대로 보내 모두 반영됨을 확인하고, 응답을 녹화해 CI 계약 시험에 넣었다(`tests/bts_responses/`의 `write_source`). S5-2에서 확인하지 못한 Redmine 상태 읽기도 이번에 실제 응답으로 바꿨다.
- **한계** — 한 사람이 이 PC에서 쓰는 전제다. 동작은 서버 프로세스 안에서 잠금 하나로 한 번에 하나씩 하지만, 같은 티켓을 BTS 화면에서 동시에 바꾸는 것까지 막지는 못한다(쓴 뒤 다시 읽어 결과를 보이는 것으로 대신한다). Jira 상태 확인은 이슈 유형별이 아니라 프로젝트의 모든 유형을 합쳐 본다(유형 이름도 언어에 따라 달라서).

### S5-2에서 확인한 것

- **끌어오기만 한다.** 서비스가 이 PC에서만 열려 있어 BTS가 변경을 알려 주는 웹훅을 받을 수 없다. QA 화면의 [지금 동기화] 버튼을 눌렀을 때만 BTS를 읽고, 화면을 여는 것만으로는 BTS를 부르지 않는다. 마지막 동기화 시각을 화면에 보인다.
- **Jira 검색은 `/search/jql`만 된다.** 예전 `/search`는 삭제돼 HTTP 410을 돌려준다(2026-11-23, 실제 KAN 공간에서 확인). 여러 티켓은 `key in (...)` 한 번으로 읽고, 없는 키는 결과에서 빠진다. 서비스가 50건씩 묶어 요청하며 한 묶음이 실패해도 나머지는 갱신한다. 읽기에 실패하거나 BTS에서 찾지 못한 티켓은 이전에 읽은 값을 그대로 두고 화면에 알린다.
- **상태 이름은 설정으로 해석한다(S5-3에서 다섯 상태로 통일하며 없앰).** BTS마다 "검증 대기"·"완료"의 이름이 달라서 `[jira.status]`·`[redmine.status]`의 verify·done 목록에 있는 이름만 그 뜻으로 보고 나머지는 "진행 중"이다. 이 섹션이 없으면 동기화하지 않는다(서버는 이전처럼 시작한다). 이름이 틀리면 대기 건이 묻히므로 화면 아래에 읽어 본 BTS 상태 이름을 그대로 보인다. 실제 KAN은 해야 할 일 / 진행 중 / 검토 중 / 완료이고 검증 대기는 "검토 중"이다.
- **상태 변화를 지금부터 쌓는다.** 동기화에서 상태가 처음이거나 바뀐 것을 발견하면 `bts_changes`에 한 줄 남긴다(S5-4c의 재오픈률·회귀 테스트 대기 시간 근거). 시각은 BTS가 바뀐 때가 아니라 우리가 읽다가 발견한 때라, 동기화 사이의 변화는 한 번으로 합쳐진다.
- **대기 시간은 BTS가 마지막으로 바꾼 뒤 경과 시간이다.** 상태가 바뀐 시각이 아니라서 검증 대기 중 코멘트가 달려도 줄어든다. 정확한 값은 S5-4c에서 상태 변화 기록으로 센다.
- **대상은 최근 200건.** 등록한 리포트 중 번호가 큰 200건만 읽고, 보드도 같은 건만 센다(더 읽어야 하면 `config.SYNC_LIMIT`을 올린다).
- **한계** — Redmine 상태 읽기는 실제 서버로 확인하지 않았다. 컨테이너를 지운 뒤라 녹화한 단건 응답과 API 문서 형식으로 만든 목록 응답으로만 시험했다. [지금 동기화]를 연달아 누르면 늦게 끝난 쪽이 더 오래된 값을 덮어쓸 수 있다(로컬 한 명 사용 전제의 한계, 문제가 되면 BTS 변경 시각이 더 오래된 값은 저장하지 않게 올린다). 재현 대기는 배정 팀이 QA이고 검증 대기·완료가 아닌 건으로 가린다. 자동 배정을 쓰지 않으면 재현 대기를 가릴 수 없다고 화면에 안내한다.

### S5-1에서 확인한 것

- **팀 관리형 Jira에는 컴포넌트가 없다.** 실제 KAN 공간을 읽어 보니 컴포넌트 목록이 비어 있고 이슈 만들기 화면에도 컴포넌트 칸이 없었다(2026-11-23). 그래서 "서비스는 팀만 표시하고 사람 배정은 BTS의 컴포넌트 기본 담당자에게 맡긴다"는 처음 안을 버리고, 서비스가 설정의 "팀 → 계정" 표로 담당자를 직접 넣는다. Jira는 계정 ID, Redmine은 사용자·그룹 번호다. 두 BTS가 같은 방식이 되어 구조가 하나로 줄었다. Jira에는 `팀_<이름>` 라벨도 붙여 BTS에서 팀별로 걸러 볼 수 있게 했다.
- **배정은 사람이 확정한 8칸으로 정한다.** 검토 화면의 기본 선택은 "규칙대로"이고, 등록하는 순간의 확정 8칸으로 다시 계산한다. 검토에서 모듈을 고친 뒤 화면을 다시 읽지 않아도 고친 모듈의 팀으로 간다. 사람이 다른 팀을 고르면 규칙의 팀과 함께 저장해 상세 화면에 "규칙: 서버 → 사람이 바꿈"처럼 보인다(S5-4c에서 비율로 센다).
- **처리 → 받는 쪽은 코드, 팀 이름은 설정.** [처리] 값마다 누가 받는지는 8칸 형식의 뜻이라 코드에 두었다(등록(재현 대기)·정보 요청 후 보류 → QA, 개발 배정·긴급 사인 요청 → 첫 모듈의 팀, 모듈이 없으면 QA, CS 응대 → CS팀, 폐기 → 배정 없음). [처리] 허용 값이 늘면 시험이 먼저 실패한다. 10개 모듈 중 하나라도 팀이 없거나 고른 BTS에 팀의 계정이 없으면 서버가 시작하지 않는다. `[assign]`을 지우면 이전처럼 배정하지 않는다.
- **연결 확인이 계정까지 본다.** `triage-serve --check`는 팀마다 적은 계정이 그 프로젝트의 담당자가 될 수 있는지 BTS에 묻는다(Jira 담당 가능 사용자 검색, Redmine 프로젝트 구성원). 실제 KAN에서 본인 계정은 통과하고 없는 계정은 걸리는 것을 확인했고, 응답을 계정 정보를 지운 채 녹화했다. 본인 계정을 "서버" 팀으로 둔 티켓 KAN-8이 담당자·`팀_서버` 라벨과 함께 등록됐다.
- **이미 있는 티켓에 연결하면 담당자를 바꾸지 않는다.** 끊긴 등록 뒤 다시 등록해 기존 티켓에 연결된 경우, 그 티켓의 담당자는 그대로 두고 "배정 적용 안 됨"으로 남긴다(독립 검토에서 발견). 등록 실패 후 검토로 되돌리면 사람이 고른 팀이 화면에 그대로 다시 보인다(독립 검토에서 발견).
- **한계** — Redmine은 컨테이너를 지운 뒤라 실제 서버로 확인하지 않았다. 구성원 목록 응답은 Redmine API 문서 형식으로 만든 시험 응답이다. 구성원 목록을 읽으려면 API 키에 구성원 관리 권한이 필요하고, 연결 확인은 구성원인지만 볼 뿐 그 역할이 "일감 할당 가능"인지는 보지 않는다. 그룹을 담당자로 넣으려면 Redmine 관리 설정 "그룹에 일감 할당 허용"이 켜져 있어야 한다. 배정이 얼마나 맞을지는 [모듈] 정답률에 달려 있다(평가 체계의 성능표).


### S5-5b에서 확인한 것

- **"나"는 BTS 토큰 주인이다(2026-11-25 경민 승인).** 동기화할 때 `tracker.me()`(계정 ID)를 읽고 QA팀 그룹 구성원에서 같은 ID의 이름을 찾아 `Syncer.me`에 기억한다. 화면을 열 때마다 BTS를 부르지 않는다. 저장된 담당자는 표시 이름이라 이름으로 비교한다. QA팀 구성원이 아니면 화면이 이유를 안내한다. 팀원별 화면은 S5-5c(팀·구성원별 부하)에서 다룬다.
- **세 구역.** ① 내 차례: QA Review는 BTS 담당자가 나인 이슈, Resolve는 QA 담당(`qa_owner`)이 나인 이슈 — 개발로 넘어가 BTS 담당자가 바뀌어도 회귀 테스트는 처음 받은 QA 담당에게 돌아온다. 서비스를 거치지 않고 BTS에서 직접 만든 이슈는 QA 담당 기록이 없어 BTS 담당자가 나인 Resolve만 센다. ② 넘긴 이슈: 서비스가 QA 담당으로 기억한 In Dev·Check. ③ 병목: 위 두 구역에서 기준을 넘긴 것을 위에 모은다.
- **머문 기간과 기준.** 그 상태로 들어온 것을 동기화가 발견한 시각(상태 변화 기록)부터, 기록이 없으면 BTS가 마지막으로 바꾼 시각부터 센다. 기준은 `config.BOTTLENECK_DAYS`: QA Review 2일, Resolve 2일, In Dev 7일, Check 14일. 발견한 시각이라 실제 변경과 최대 동기화 간격(10분)만큼 어긋날 수 있다(S5-4c와 같다).
- **구조.** 계산은 `sync.mine()`, 화면(`/mine`, `mine.html`)은 결과만 보여 준다. BTS 계약·DB 표는 바꾸지 않았다. 가짜 BTS의 상태 조회가 담당 팀 대신 담당 구성원을 돌려주도록 고쳤다(실제 Jira·Redmine과 같게).
- **실제 BTS.** 실제 Jira KAN을 연결해 화면을 확인했다(내 차례 KAN-9 QA Review, 머문 0.8일).
- **한계** — 이름이 같은 구성원 둘을 구분하지 못한다(담당자 ID도 저장하면 해결). "넘긴 이슈"는 서비스를 거친 건만 센다. QA 담당 기록이 없는 In Dev는 누가 넘겼는지 알 수 없다. 서버를 다시 켜면 첫 동기화가 끝날 때까지 "읽는 중"으로 보인다.

## 7. QA 실무 경험과 부트캠프 학습의 활용

- **QA 실무**: 라이브 서비스 QA에서 리포트는 게시판·디스코드·커뮤니티로 들어와 사람이 BTS로 옮겨 적는다. 이 옮겨 적기와 1차 분류를 자동화하되, 등록 직전에 사람이 확인하는 지점(검토 큐)을 남긴 것은 오등록 비용이 크다는 실무 판단이다. BTS가 회사마다 다르다는 경험이 어댑터 구조의 근거다.
- **부트캠프 Private LLM 트랙**:
  - FastAPI·Pydantic 계약 설계는 데이터 파이프라인·FastAPI 과목에서 배웠다.
  - 신뢰 경계·개인정보 가리기·출력 검증은 LLMOps 4장에서 배웠다.
  - 운영 지표(p95·오류율·분모 표기)는 LLMOps 3장에서 배웠다.
  - 입력 정리 순서와 토큰 예산은 컨텍스트 엔지니어링에서 배웠다.
  - 수집 전 리스크 점검은 데이터 수집 과목에서 배웠다.
  - 영역별 계약(`contracts.py`)과 설정 한 곳(`config.py`)은 3차 팀 프로젝트의 구조를 따랐다.
