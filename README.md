# LLM 트리아지 평가 체계

> **로컬 LLM이 버그 리포트를 1차 트리아지(분류·우선순위·처리 경로 결정)하는 파이프라인과, 그 판단을 믿을 수 있는지 숫자로 검증하는 평가 체계**
>
> 검증 사례: 가상 게임 "Aether Raid" 라이브 서비스의 버그 리포트. 판정 기준과 평가셋은 게임 개발 QA 실무 기준에서 출발했습니다.

> **30초 요약**
> * **무엇을 하나**: 버그 리포트 한 건을 받아 8칸 티켓(요약·분류·모듈·우선순위·재현 정보·발생 빈도·처리·누락 정보 및 권장 조치)으로 만듭니다. 모델은 8GB VRAM 노트북에서 도는 `qwen2.5:7b`(Ollama)입니다
> * **구조**: 모델은 판단하고, 형식과 절차는 코드가 강제합니다 — 프롬프트 → 칸 재요청 → Critical 체크리스트 → 폐기 확인 → 후처리 안전장치
> * **성능 (처음 보는 60건 × 6회)**: 결함 폐기 **0건**, 형식 완전 준수 99.7%, 처리 정답 61.1%, Critical 미상신 19/96, 사람이 확인한 날조 23응답
> * **사용 전제**: Critical 누락과 날조가 남아 있어 **사람이 모든 응답을 확인합니다.** 사람 확인을 줄이는 장치(LLM 채점관, 자동 등록 라우팅)는 측정했지만 사전 기준을 넘지 못해 채택하지 않았습니다
> * **검증 방식**: 기준은 측정 전에 커밋하고, 최종 평가용 세트는 한 번만 실행하고, 바뀐 구성은 seed 3개 회귀 게이트로 판정합니다
> * **작업 페이지 (구현 중)**: 리포트를 붙여 넣으면 같은 파이프라인으로 트리아지하고, 사람이 8칸을 확인·수정한 뒤 BTS에 등록합니다. Jira Cloud·Redmine에 실제로 등록하는 것까지 확인했습니다

## 1. 문제와 접근

1차 트리아지는 들어오는 건을 분류하고, 우선순위를 매기고, 어디로 보낼지 정하는 일입니다. 위험한 건을 놓치면 장애로 이어지고, 모든 건을 사람에게 올리면 검토가 병목이 됩니다.

라이브 서비스 게임에는 하루 수백~수천 건의 리포트가 들어오고, 대다수는 짧거나 모호하거나 여러 결함이 섞여 있습니다. 이 일을 LLM에 맡기려 할 때 제약이 하나 있습니다. **리포트에는 유저 계정 정보와 미출시 콘텐츠가 들어 있어 외부 API로 보낼 수 없습니다.** 그래서 사내에서 도는 로컬 모델이어야 하고, 담당자 노트북(8GB VRAM)에서 돌 수 있어야 합니다.

모델은 `qwen2.5:7b`(Q4_K_M)입니다. v1.0에서 `llama3.1:8b`와 비교했을 때 Llama는 짧은 리포트에 없는 결함과 PC 사양을 지어냈고, v1.4에서 후보 8개를 다시 걸렀을 때도 사전에 정한 교체 규칙을 만족한 모델이 없었습니다.

* **수행 형태**: 1인 프로젝트 (평가셋 설계, 파이프라인, 평가 자동화, 정량·정성 평가)
* **실행 환경**: Windows 11, NVIDIA GeForce RTX 5060 Laptop GPU (VRAM 8,151 MiB), RAM 31.4 GB, Ollama, Python 3.12 (`uv`)

## 2. 구조

### 1) 리포트 한 건이 거치는 단계

| 단계 | 담당 | 하는 일 | 쉽게 말하면 |
| :--- | :--- | :--- | :--- |
| 1. 1차 판정 | 모델 | 판정 기준서를 요약한 프롬프트(v2.3)로 8칸을 채움 | 담당자의 첫 판정 |
| 2. 칸 재요청 | 코드 | 허용 값 밖인 칸만 JSON 스키마(enum·pattern)로 한 번 다시 받음 | 양식이 틀린 칸만 반려 |
| 3. Critical 체크리스트 | 모델 답 + 코드 판정 | 결함으로 분류된 건에 체크리스트 질문 6개("유료 결제에 피해가 있는가" 등, 대부분 예/아니오)를 묻고, 해당 답이 있으면 코드가 Critical로 올림. 내리지는 않음 | 심각도 체크리스트 |
| 4. 폐기 확인 | 모델 답 + 코드 판정 | 폐기하려는 건에 이상 현상 제보인지 한 번 더 물음 | 닫기 전 재확인 |
| 5. 후처리 안전장치 | 코드 | `[처리]` 규칙 보정 — Critical은 리드 QA 사인을 거치는 `긴급 사인 요청`으로 보냄 (정답 라벨은 보지 않음) | 등록 전 절차 점검 |

실행 기록에는 모델 원본 응답과 단계별 개입 내역이 함께 남습니다. 그래서 모델의 실력과 코드 보정의 효과를 따로 셀 수 있습니다.

### 2) 코드

```
src/triage_eval/
├─ config.py       모델·생성 옵션·파일 위치 (경로는 이 파일에서만 정한다)
├─ contracts.py    8칸 출력 형식·허용 값·형식 규칙 R1~R7
├─ llm.py          Ollama 호출 입구
├─ triage/         리포트 한 건 처리 — triage() 하나로 위 5단계를 끝까지
│   prompt.py · checklist.py · guardrail.py · pipeline.py
└─ evaluation/     평가
    runner.py (triage-run) · performance.py (triage-eval) · gate.py (triage-gate)
    score.py (채점) · hallucination.py (규칙 기반 날조 탐지) · environment.py (측정 환경 점검)
```

```
src/triage_service/          작업 페이지 서비스 — 위 triage() 를 그대로 호출
├─ contracts.py    Report · Issue · Ticket, 출처·BTS 계약(Source · Tracker)
├─ intake/         출처 — 붙여넣기, Jira·Redmine 이슈·게시판 글·디스코드 메시지 링크, 접수 흐름(reception.py)
├─ worker.py       작업자 하나가 차례대로 트리아지
├─ routing.py      자동 등록 / 검토 결정 (지금은 모든 건을 사람 검토로)
├─ flow.py         상태: 접수 → 트리아지 중 → 검토 대기 → 등록 완료 / 폐기 / 실패
├─ review.py       사람이 고친 8칸을 형식 규칙으로 검사해 등록
├─ assign.py       생성 시 자동 배정 — 재현이 필요하면 QA팀, 개발로 넘기면 모듈의 팀
├─ sync.py         BTS 상태 동기화와 QA 보드 — 재현 대기·회귀 테스트 대기·보류·팀별 미해결
├─ qa.py           QA 동작 — 재현 확인·회귀 테스트 통과·실패·보류·코멘트를 BTS 에 쓰기
├─ store.py        SQLite (모델 8칸 · 확정 8칸 · 고친 칸 · 상태 변경 이력 저장)
├─ metrics.py      대시보드 지표 (상태별 건수, 유입, 분포, 사람 수정 비율, 처리 시간 p50·p95, 마일스톤별 QA 지표)
├─ bts/            BTS 어댑터 — Jira Cloud · Redmine · 가짜 BTS, 접속 함수(clients.py), 설정 검사
├─ web/            화면 — FastAPI + Jinja2 (결과를 보여 주기만)
└─ cli.py          실행 명령 (uv run triage-serve [--check])
```

각 파일 맨 위 `[설계 의도]`에 "왜 이렇게 했는가"를 번호로 적어 두었습니다.

## 3. 성능

방법과 모델을 고르는 동안 한 번도 실행하지 않은 **최종 평가용 60건**을 seed 1·11·21 × 2회로 한 번만 실행했습니다. 개발용 63건(여러 번 보며 구성을 고른 문항)은 비교용입니다. **실제 성능에 가까운 쪽은 최종 평가용입니다.**

| 지표 | 최종 평가용 60건 × 6회 (360응답) | 개발용 63건 × 6회 (378응답) |
| :--- | ---: | ---: |
| 형식 완전 준수 | 99.7% | 100.0% |
| 처리 정답 | 61.1% | 73.3% |
| 분류 정답 | 73.1% | 65.3% |
| 우선순위 정답 | 61.9% | 62.7% |
| 모듈 정답 | 73.6% | 75.9% |
| **X-1 Critical 미상신** (놓친 응답 / Critical 응답) | **19 / 96** | 14 / 102 |
| X-2 결함을 폐기 | 0 / 264 | 0 / 258 |
| X-3 사람 확인 없이 종결 (판단이 갈리는 경계 건을 확정 처리) | 15 / 60 | 14 / 60 |
| 과잉 상신 (정답 처리가 긴급 사인 요청이 아닌 건을 긴급 사인 요청) | 20 | 28 |
| 날조 — 규칙 탐지기 | 0 | 0 |
| 날조 — 사람 확인 (검토자 1명) | 23응답 | (측정 안 함) |
| 평균 응답 시간 | 2.44초 | 2.27초 |

> 위 표는 저장소의 실행 기록을 `uv run triage-eval`로 다시 채점한 값이고, 시험(`tests/test_runner.py`)이 최종 평가용 채점 결과를 고정합니다. 위험 건은 비율이 아니라 **놓친 건수**로 셉니다.

### 남은 한계

* **Critical 미상신.** 처음 보는 리포트에서 Critical 응답 96건 중 19건을 긴급 사인 요청으로 보내지 않았습니다. 체크리스트의 효과는 개발용 문항에서만 확인됐습니다.
* **날조 탐지.** 규칙 탐지기는 한 건도 잡지 못했지만, 검토자 1명이 요약을 확인하니 23응답(12묶음)에서 날조가 있었습니다. 확인자가 한 명이라 판단에 주관이 들어갈 수 있습니다. LLM 채점관(gemma4:12b)도 사람 판단과 일치도가 낮아(κ 0.18) 채택하지 않았습니다. 날조 확인은 사람이 합니다.
* **누락 정보 칸이 거의 비어 있음.** 최종 평가용 360응답 중 336건이 `[누락 정보 및 권장 조치]`에 "없음"·"해당 없음"만 적었습니다. 정답표가 요구하는 요청·권장 문구의 반영률은 최종 평가용 0%, 개발용 21.8%입니다.
* **자동 등록 라우팅 미채택.** 확신 신호로 자동 등록할 응답을 골랐을 때, 위험·날조 응답 56건 중 32건(57.1%)이 검토 없이 통과했습니다(사전 기준 50% 이하).
* **정답표의 흔들림.** 외부 QA 2명의 판정과 정답표의 일치율이 사전 기준에 못 미쳐 기준서를 v1.5로 고쳤습니다. 라우팅 판정은 기준서와 다른 판단을 따른 3문항에 민감했습니다.
* **검증한 도메인은 게임 버그 리포트 하나입니다.** 판정 기준서·출력 형식·모듈 목록이 게임 도메인에 맞춰져 있습니다.

## 4. 사용법

### 1) 설치

* Python 3.12 이상, [`uv`](https://docs.astral.sh/uv/), [Ollama](https://ollama.ai/)

```powershell
ollama pull qwen2.5:7b
git clone https://github.com/kokoball-eval/llm-triage-eval.git
cd llm-triage-eval
uv sync
```

### 2) 실행 → 채점 → 회귀 판정

```powershell
# 개발용 63건 × 2회 실행 (seed N, N+1). --strict-env: 다른 프로그램이 GPU를 쓰거나 배터리 구동이면 멈춤
uv run triage-run --seed 1 --strict-env
uv run triage-run --seed 11 --strict-env
uv run triage-run --seed 21 --strict-env

# 성능표 — 실행 기록을 정답표로 채점
uv run triage-eval --log 데이터/새실행/<실행 기록>.json

# 회귀 판정 — 채택 구성(기준선)보다 나빠졌는지, seed 3개 모두 통과해야 PASS
uv run triage-gate --candidate <seed1 기록> --candidate <seed11 기록> --candidate <seed21 기록>
```

* 실행 기록은 `데이터/새실행/`, 게이트 결과는 `데이터/게이트결과/`에 새 파일로 저장됩니다.
* 최종 평가용 문항은 `--split final --final`을 함께 줘야만 실행됩니다. 구성을 고치면서 최종 평가 점수를 보면 그 문항에 맞춰 고치게 되기 때문입니다. 기본 평가셋에 든 최종 평가용 문항은 v1.4의 25건이고, 새 60건은 `--dataset 데이터/평가셋/최종용_60건.json`으로 지정합니다. 두 세트 모두 이미 한 번 실행했으므로 새 구성의 최종 평가에는 새 세트를 만들어 씁니다.
* 다른 정답표로 채점하려면 `triage-eval --labels <평가셋.json>`을 씁니다. 실행 기록의 문항이 정답표에 없으면 채점하지 않습니다.

### 3) 작업 페이지

```powershell
uv run triage-serve      # http://127.0.0.1:8000
```

1. **새 리포트**에 링크를 넣고 [가져오기]를 누르거나(Jira·Redmine 이슈, 게시판 글, 디스코드 메시지), 입력 종류(커뮤니티 제보 / QA 이슈)와 제목·본문을 직접 넣습니다. 가져온 내용은 바로 접수되지 않고 입력 칸에 채워지며, 사람이 확인·수정한 뒤 [트리아지]를 누릅니다. 입력 칸은 측정한 프롬프트가 받는 칸과 같고, 본문은 1,000자까지 받습니다(측정한 리포트는 438자 이하).
2. 트리아지가 끝나면 **검토 대기**가 됩니다. 선택지 칸은 허용 값만 고를 수 있고, 고친 칸은 고치기 전 값과 함께 저장됩니다.
3. [BTS 등록]을 누르면 형식 규칙(R1~R7)을 통과한 경우에만 등록되고 티켓 번호가 붙습니다. 등록하기 전에 같은 리포트의 티켓이 이미 있는지 서비스 표식으로 먼저 찾아, 있으면 새로 만들지 않고 연결합니다.
4. 자동 배정을 켜 두면(`[assign]`) 티켓이 담당 팀에 배정됩니다. [처리]가 등록(재현 대기)·정보 요청 후 보류면 QA팀, 개발 배정·긴급 사인 요청이면 첫 [모듈]의 팀(클라·서버·아트·기획 등)입니다. 검토 화면에서 팀을 바꿀 수 있습니다. 실제 사이트에서 쓰려면 `[assign]`과 `[jira.teams]`(또는 `[redmine.teams]`)를 `설정/bts_매핑.local.toml`에 옮겨 적고 `--check`로 계정을 확인합니다. Jira는 `팀_<이름>`·`모듈_<이름>` 라벨로, Redmine은 팀 이름과 같은 일감 범주와 "모듈" 사용자 정의 필드(`module_field_id`)로 팀·모듈을 표시해 두 BTS 모두에서 걸러 볼 수 있습니다.
5. BTS 티켓 상태는 다섯 단계입니다: **QA Review**(QA 재현 확인 중) → **In Dev**(개발 대응 중) → **Resolve**(수정 완료, 회귀 테스트 필요) → **Closed**(종료), 그리고 **Check**(사유가 있어 대응 보류). Jira·Redmine 워크플로에 이 다섯 상태를 만들어 두고 `--check`로 확인합니다. 새 티켓은 [처리]에 맞는 첫 상태로 만들어집니다(재현이 필요하면 QA Review, 개발로 넘기면 In Dev, CS 응대는 QA 재현이 필요할 때만 QA Review이고 아니면 Check).
6. 첫 화면·QA 화면(`/qa`)·대시보드를 열 때 마지막 동기화가 10분보다 오래됐으면 서비스가 뒤에서 BTS를 다시 읽고, QA 화면의 [지금 동기화]로 바로 읽을 수도 있습니다. 모든 화면 머리 오른쪽에 BTS 연결 상태(연결됨·일부 실패·연결 안 됨·읽는 중, 마지막으로 읽은 때)가 보입니다. 등록한 티켓의 BTS 상태를 읽어 재현 대기·회귀 테스트 대기·보류·팀별 미해결로 보여 줍니다. 상세 화면에서 재현 확인(→ In Dev, 모듈 팀으로), 회귀 테스트 통과(→ Closed)·실패(→ In Dev), 보류(→ Check), 코멘트를 BTS에 씁니다. 보내기 직전에 BTS 상태를 다시 읽어 그사이 바뀌었으면 보내지 않고, 보낸 결과는 QA 기록에 남습니다.
7. 마일스톤은 BTS 버전입니다(Jira 릴리스, Redmine 목표 버전). [지금 동기화]가 출시 전 버전마다 그 버전의 BTS 티켓 전체를 읽고, **첫 화면 맨 위 카드**에 현재 마일스톤의 Closed 수·완료율, QA가 회귀 통과로 닫은 수, 재오픈 수, 남은 건수, 출시일까지 남은 날을 보여 줍니다. 검토 화면에서 등록할 티켓의 마일스톤을 고릅니다.

**BTS 연결** — 어느 BTS에 등록할지는 설정 파일로 정합니다. 코드는 고치지 않습니다.

| 파일 | 내용 | git |
| :--- | :--- | :--- |
| `설정/bts_매핑.toml` | 예시 설정: 사용할 BTS(`fake`·`jira`·`redmine`), 주소, 프로젝트, 우선순위 대응, 자동 배정(모듈 → 팀, 팀 → 계정) | 올림 |
| `설정/bts_매핑.local.toml` | 실제 사이트 설정 (있으면 이 파일을 먼저 읽음) | 올리지 않음 |
| `.env` | 토큰 — `JIRA_EMAIL`·`JIRA_API_TOKEN` 또는 `REDMINE_API_KEY` | 올리지 않음 |

```powershell
uv run triage-serve --check   # 서버를 띄우지 않고 설정·토큰·검색 권한, 자동 배정 계정, BTS 다섯 상태만 확인
```

설정에 모르는 키가 있거나 우선순위 대응이 빠졌거나 토큰이 없으면 서버가 시작하지 않습니다.

**링크 출처** — 가져올 수 있는 곳은 `설정/출처.toml`(실제 값은 `설정/출처.local.toml`, git 제외)에 적은 곳뿐입니다. Jira·Redmine 주소와 토큰은 BTS 설정의 것을 쓰고, 게시판은 사이트별 CSS 선택자(제목·본문·작성 시각)를 설정에 적습니다. 디스코드는 `.env`의 `DISCORD_BOT_TOKEN`(회사 봇)이 있어야 켜집니다.

* 설정에 없는 호스트·경로의 링크는 요청하지 않고, 다른 주소로 넘기는 응답(리다이렉트)은 따라가지 않으며, 응답 크기에 상한이 있습니다.
* 게시판 구조가 설정과 다르면 대신 채운 내용을 만들지 않고 실패를 알립니다. 실패하면 본문 붙여넣기로 이어 갑니다.
* 같은 원문 링크는 한 번만 접수합니다. 작성자 닉네임은 가져오지 않습니다.

* 자동 등록은 없습니다. 모든 건이 사람 검토를 거칩니다(라우팅 미채택, [3절](#3-성능)).
* 트리아지가 실패하면 `실패` 상태와 오류 내용이 남고, [다시 시도]로 처음부터 다시 처리합니다. BTS 등록이 실패한 건은 [검토로 되돌리기]로 확정한 8칸을 그대로 둔 채 다시 등록합니다(모델을 다시 돌리지 않음).
* BTS 응답이 끊기면 "등록 여부 불확실"로 남기고 자동으로 다시 보내지 않습니다. 다시 등록할 때 표식으로 기존 티켓을 먼저 찾아 중복을 막습니다. 다만 Jira는 등록 직후 검색에 바로 나타나지 않을 수 있어, 끊긴 직후에는 Jira에서 먼저 확인한 뒤 다시 등록합니다.
* **대시보드**(`/dashboard`)는 상태별 건수, 일자별 유입, 확정 8칸 분포, 사람 수정 비율(칸별, Critical로 올린·내린 건), 자동 처리율(0%), 처리 시간(트리아지·검토 대기·접수→등록의 중앙값과 p95), 실패를 보여 줍니다. 모든 비율에 분모를 함께 표시하고, 기간(7일·30일·전체)을 고를 수 있습니다. 마일스톤별 QA 지표(회귀 테스트 대기 건수·시간, 재오픈률, BTS 팀 표식 기준 팀별 미해결, 배정 팀을 사람이 바꾼 비율)도 함께 보입니다.
* 다른 사이트에서 보낸 요청(Origin·Referer가 다른 POST)과 127.0.0.1·localhost가 아닌 Host로 온 요청은 받지 않습니다.
* DB는 `데이터/서비스/`에 생기며 git에 올리지 않습니다(리포트 원문에 유저 정보가 들어갈 수 있음).

## 5. 어떻게 믿을 수 있게 했나

| 장치 | 하는 일 | 왜 |
| :--- | :--- | :--- |
| 사전 등록 | 채택 기준과 계획을 측정 전에 커밋하고, 결과를 본 뒤 바꾸지 않음 | 결과에 맞춰 기준을 옮기면 무엇이든 "통과"가 됨 |

| seed 3개 회귀 게이트 | 기준선과 같은 seed끼리 비교해 위험 누락·칸 정답·문항 단위 회귀를 판정 | seed 하나로는 효과와 우연을 구분할 수 없음 |

| 한 번에 하나만 변경 | 방법·모델·프롬프트를 따로 비교 | 여러 개를 함께 바꾸면 무엇이 결과를 바꿨는지 모름 |
| 정답표 검증 | 외부 QA 2명이 같은 기준서로 따로 판정해 일치율(κ)을 잼 | 정답표가 틀리면 모델 점수도 틀림 |

## 7. 다음 단계

* **서비스 구현** — 리포트 링크를 붙여 넣으면 본문을 가져와 트리아지하고, 사람이 확인·수정한 뒤 BTS(Jira·Redmine)에 등록하는 작업 페이지와 처리 현황 대시보드입니다. 출처와 BTS를 어댑터로 분리해 파일 하나 단위로 바꿔 끼웁니다 (→ [서비스 설계](문서/서비스_설계.md)).
  * S1 뼈대(본문 붙여넣기 → 트리아지 → 사람 검토 → BTS 등록), S2 Jira Cloud·Redmine 연결, S3 링크 가져오기(Jira·Redmine 이슈, 게시판 글, 디스코드 메시지), S4 대시보드를 구현했습니다. 위 한계 때문에 모든 응답을 사람이 확인하는 흐름입니다.
  * S4 처리 현황 대시보드까지 구현해, 설계 문서의 S1~S4가 모두 끝났습니다. 디스코드 실제 연결은 회사 봇 토큰이 있으면 설정에서 켭니다.
  * S5는 QA가 BTS를 따로 열지 않고 서비스 안에서 일하게 하는 단계입니다. S5-1 생성 시 자동 배정, S5-2 BTS 상태 동기화·QA 보드, S5-3 QA 동작(재현 확인·회귀 테스트 통과·실패·보류·코멘트, BTS 상태 다섯 단계 통일), S5-4a Jira·Redmine 동기화 차이 줄이기, S5-4b 마일스톤 성과(첫 화면), S5-4c 대시보드 QA 지표, S5-4d 화면을 열 때 자동 동기화·BTS 연결 표시를 구현했고, 이어서 팀을 BTS 그룹으로 두고 구성원에게 배정하는 구조와 "내 담당" 화면(S5-5)을 진행합니다.
* **기준서 v1.6 후보** — 크로스 플랫폼 재현 확인, 라벨 재검토, 라우팅 신호 개선, 누락 정보 칸 등 (→ [기준서 v1.6 후보](문서/기준서_v1.6_후보.md)).
