## ISSUE-002 · 허용폭과 정확히 같은 변화가 FAIL 판정됨 (부동소수점 경계값)

| 항목 | 내용 |
| :--- | :--- |
| 심각도 | Minor — 경계값에서만 발생하는 잘못된 FAIL |
| 발견 | 2026-09-30, 단위 테스트 작성 중 (경계값 분석) |
| 조치 커밋 | `1936444` |
| 회귀 테스트 | `tests/test_compare_runs.py::test_exactly_at_tolerance_passes` |

**현상** — 평균 지연이 허용폭(+20%)과 **정확히 같게** 늘어난 경우 통과해야 하는데 FAIL이 났습니다. 화면에는 "변화 +20.0% (허용 악화폭 20.0%)"로 표시되면서 FAIL이 뜨는, 보는 사람에게는 모순인 결과였습니다.

**원인** — `(1.668 − 1.39) / 1.39 × 100`이 이진 부동소수점에서는 `20.000000000000004`로 계산되어 `≤ 20.0` 비교에서 거짓이 됐습니다. 화면 표시는 소수 첫째 자리로 반올림하고 비교는 반올림 없이 하고 있어서, **보이는 값과 판정에 쓰는 값이 서로 달랐습니다.**

**조치** — 변화율을 소수 둘째 자리로 반올림한 뒤 허용폭과 비교합니다. 반올림에는 문서 수치와 같은 half-up 함수(`summarize_eval.rnd`)를 씁니다.

**재발 방지** — 경계값 테스트를 회귀 테스트로 남겼습니다. 반올림을 빼는 변경을 일부러 넣어 보면 이 테스트가 실패하는 것까지 확인했습니다.

## ISSUE-005 · README 굵은 글씨 깨짐, 표 칸 안 줄바꿈

| 항목 | 내용 |
| :--- | :--- |
| 심각도 | Trivial — 표시 문제 |
| 발견 | 2026-09-30, GitHub 화면에서 README를 직접 확인하다 발견 |
| 조치 커밋 | `9773f3a` |

**현상**
1. `**"LLM에게 … 평가 체계"**로`가 굵게 표시되지 않고 `**` 기호가 그대로 보였습니다. 1절의 `**"Aether Raid"**의`도 같은 문제가 있었습니다.
2. 로드맵 표의 "상태" 칸이 좁아 `완료`가 `완/료`로 쪼개져 표시됐습니다.

**원인**
1. 마크다운(CommonMark)은 **닫는 `**` 바로 앞이 문장부호(`"`)이고 바로 뒤가 글자(`로`)이면 굵은 글씨로 인식하지 않습니다.** 영어는 보통 뒤에 공백이 오지만, 한국어는 조사가 바로 붙어서 이 규칙에 자주 걸립니다.
2. 한국어는 글자 단위로 줄이 바뀔 수 있어서, 좁은 표 칸에서 단어가 쪼개집니다.

**조치**
1. 따옴표를 굵은 글씨 밖으로 뺐습니다: `"**…평가 체계**"로`
2. 상태를 버전 앞 아이콘으로 합쳤습니다(`✅ v1.0`). 아이콘과 버전 사이에는 줄바꿈 없는 공백(`&nbsp;`)을 넣었습니다.

**재발 방지** — README를 고칠 때 마크다운 렌더러로 전체 파일을 변환해서 풀리지 않은 `**`이 0개인지 확인합니다.

## ISSUE-006 · 환각 탐지기 오탐 2건 (출시 전 단위 테스트에서 발견)

| 항목 | 내용 |
| :--- | :--- |
| 심각도 | Minor — 근거 있는 응답을 날조로 오판 (게이트가 정상 응답을 FAIL 낼 수 있음) |
| 발견 | 2026-10-01, v1.2 환각 탐지기 단위 테스트 작성 중 (커밋 전) |
| 회귀 테스트 | `tests/test_detect_hallucination.py::test_fact_present_in_input_is_grounded`, `::test_quantity_must_match_exactly` |

**현상**
1. 입력에 "v2.3.1"이 있고 응답이 "v2.3.1 회귀 테스트 권장"이라고 쓰면, 버전 번호 일부와 "회귀"의 "회"가 합쳐져 **"3.1 회"라는 횟수**로 뽑히고 날조로 판정됐습니다.
2. 입력이 "15초 후에 멈춤"이면 응답의 **"5초"가 근거 있음**으로 판정됐습니다. "15초"라는 글자 안에 "5초"가 들어 있기 때문입니다.

**원인** — 수치 패턴이 앞뒤 문맥을 보지 않았습니다. 1번은 숫자 앞의 마침표(버전 번호의 일부)와 단위 뒤의 글자("회귀")를, 2번은 근거를 찾을 때 숫자 앞에 다른 숫자가 붙어 있는지를 확인하지 않았습니다.

**조치** — 수치 패턴에 "앞에 숫자·마침표가 붙지 않을 것", "`회` 뒤에 `귀`가 오지 않을 것"을 추가하고, 수치의 근거 확인도 "앞에 숫자가 붙지 않은 같은 수치"가 입력에 있을 때만 인정하도록 바꿨습니다.

**재발 방지** — 두 경우를 테스트로 고정했습니다. 수정 후 실제 로그 85건에서 탐지 결과가 기대(Llama Q08 4건, 그 외 0건)와 같은 것도 다시 확인했습니다.

> 지금까지의 실제 로그 85건에는 두 형태가 없어 수치에 영향을 준 적은 없습니다. 다만 "v2.3.1 회귀 테스트 권장"은 트리아지 응답에서 흔한 표현이라, 그대로 두었다면 평가셋을 늘리는 v1.3에서 정상 응답을 FAIL로 만들었을 가능성이 높습니다.

**조치하지 않은 이유** — 이 측정 전에 "결과를 보고 프롬프트·안전장치·채점기를 고치지 않는다"고 정했다. 탐지기를 고치면 v1.3 최종 수치가 바뀌므로, 측정값(날조 2건)은 그대로 기록하고 오탐이라는 판단과 근거를 함께 남긴다.

**현상** — 같은 조건(`num_ctx` 8192, 생각 끄기)으로 모델을 올린 뒤 측정했다.

| 모델 | `ollama ps` SIZE / PROCESSOR | nvidia-smi VRAM 사용량 | 생성 속도 |
| :--- | :--- | ---: | ---: |
| qwen2.5:7b | 5.0 GB / 100% GPU | 4,876 MiB | 70.9 tok/s |
| qwen3.5:9b | 6.3 GB / 12%/88% CPU/GPU | — | — |
| gemma4:12b | **939 MB** / 100% GPU | 6,750 MiB | 29.4 tok/s |

**해석** — gemma4:12b는 Ollama가 939 MB로 보고하지만 실제 VRAM 사용량은 6,750 MiB다. PROCESSOR 칸도 같은 크기 값으로 계산되므로 이 계열에서는 신뢰할 수 없다. VRAM에 1.4 GB 여유가 있고, 생성 속도가 CPU 넘침이 확인된 qwen3.5:9b처럼 급락하지 않아 전량 GPU 적재로 판단했다. qwen2.5:7b와 qwen3.5:9b는 ps 값과 실제가 맞았다.

**결론** — 모델 계열에 따라 외부 도구의 보고값이 실제와 다를 수 있다. 사전 점검은 ps 값과 독립된 측정값을 함께 기록하도록 바꿨다([ISSUE-009](#issue-009)).

## ISSUE-011 · 마지막 모델이 메모리에 남아 다음 실행의 측정 환경 점검이 실행을 거부

| 항목 | 내용 |
| :--- | :--- |
| 심각도 | Minor — 실행이 시작되지 않을 뿐 잘못된 측정은 생기지 않음 |
| 발견 | 2026-10-04, v1.4 실험 B (seed 1 → 11 연속 실행) |
| 대응 | 우회: 실행 전 `ollama stop <모델>` (v1.4). 코드 수정: v1.5 |

**현상** — 실험 B를 seed 1·11·21로 연속 실행하자 seed 1은 정상으로 끝났지만, seed 11·21은 측정 환경 점검에서 "다른 프로그램이 VRAM 5,876 MiB를 쓰고 있다"는 경고로 `--strict-env`에 막혔다. 비교 도구는 seed가 빠졌다며 판정을 거부했다.

**원인** — `run.py`는 모델마다 실행 전에 그 모델을 메모리에서 내리지만, 실행이 끝난 뒤 마지막 모델은 내리지 않는다. Ollama는 마지막 모델을 기본 5분간 유지한다. 측정 환경 점검은 "GPU 사용량 − Ollama가 보고한 모델 크기"를 다른 프로그램의 사용량으로 계산하는데, gemma4 계열은 Ollama가 크기를 실제보다 작게 보고하므로([OBS-003](#obs-003)) 남은 모델의 일부가 다른 프로그램으로 잡혔다. 실험 A와 모델 재선정에서는 마지막 모델이 qwen2.5·granite4여서 드러나지 않았다.

**조치** — 각 seed 실행 전에 `ollama stop`으로 모델을 내리고 seed 11·21을 다시 실행했다. 실행 도중 코드를 바꾸면 seed마다 조건이 달라지므로 코드는 고치지 않았다.

**재발 방지 (v1.5)** — 실행이 끝나면 마지막 모델도 메모리에서 내린다. 측정 환경 점검 메시지에 "Ollama가 보고한 모델 크기와 GPU 사용량이 크게 다르면 남은 모델일 수 있다"는 안내를 더한다.

**코드 수정 (v1.5)** — `run.py`가 모든 응답을 받은 뒤 사용한 모델을 모두 메모리에서 내린다(설계 의도 13). 응답을 다 받은 뒤에 내리므로 응답 내용은 바뀌지 않고, 실행 기록의 설정 항목도 더하지 않아 기존 실행 기록과의 비교 조건이 그대로다. 측정 환경 점검(`preflight.py`)은 VRAM 경고가 났을 때 Ollama에 올라가 있는 모델이 있으면 "남은 모델일 수 있으니 `ollama stop`으로 내린 뒤 다시 실행"하라는 안내를 덧붙인다. 경고의 개수와 판정은 바꾸지 않았다. 두 동작은 가짜 모델로 실행이 끝난 뒤 모든 모델을 내리는지, 남은 모델이 있을 때만 안내가 붙는지를 확인하는 테스트로 고정했다. 실제 모델 실행에서 응답이 바뀌지 않았는지는 채택 구성 회귀 게이트의 기준선 재현 점검에서 함께 확인한다.

**확인 (2026-10-08)** — 기준선 재현 점검에서 seed 11 → 21을 `ollama stop` 없이 연속 실행했고, 두 번째 실행도 측정 환경 점검을 경고 없이 통과했다. 세 실행의 모델 원본·최종 응답은 기준선과 126/126 같아, 수정이 응답을 바꾸지 않았음도 확인했다.

**현상** — 계획(§5)은 검토자 채점과 채점관 프롬프트 개발을 따로 진행하고, 검토자는 채점관의 판정을 보기 전에 채점을 마치도록 정했다. 프롬프트 개발 중 개발용 자료(seed 11)의 판정 결과를 대화로 보고하면서, 채점관이 놓친 사례로 A06 요약의 어느 부분이 원문과 어긋나는지를 설명했다. 측정 세트(seed 1)의 A06 요약도 같은 부분을 포함하고 있었고, 그 설명은 측정 세트를 채점 중이던 검토자에게 전달되었다. 같은 보고에서 주입 대상에서 뺀 문항 번호 3개도 전달되어, 그 3건이 자연 응답이라는 것을 검토자가 알 수 있었다.

**원인** — 개발용 자료와 측정 세트가 같은 리포트 63개를 쓰고(계획 §8의 알려진 한계), 개발용에서 측정 세트와 글자까지 같은 요약만 뺐다. 내용이 같은 다른 문장은 남아 있었다. 개발 결과를 보고할 때 "측정 세트에 같은 리포트가 있으면 내용을 말하지 않는다"는 규칙이 없었다.

**조치** — 측정 전에 A06을 자연 응답 지표에서 뺐다(42건). 기준 값은 바꾸지 않았다. 측정 세트에 대한 채점관 판정을 보기 전에 노출 사실만으로 정했고, 계획에 추가 기록으로 남겼다. 같은 대화에서 언급된 다른 개발용 리포트 2개는 측정 세트의 요약 내용이 달라 판정이 노출되지 않았으므로 지표에 남겼다. 채점관 실행 코드의 설명과 변경 이력에서는 개발용 판정 내용을 빼고, 검토자 채점이 끝난 뒤 결과 보고서에 적기로 했다.

**재발 방지** — 사람 채점과 모델 개발을 동시에 진행할 때는, 채점이 끝날 때까지 개발 결과를 건수(검출 수·오류 수)로만 보고하고 문항·요약 내용은 말하지 않는다. 측정 도구는 결과를 남기기 전에 제외 문항이 주입 문항이 아닌지 확인하고(자연 응답만 뺄 수 있음), 뺀 문항의 판정을 결과에 따로 기록한다(`judge.py` 설계 의도 11).
