# v1.5 라벨 일치율 결과 보고서 — 정답표를 다른 QA에게 검증받다

> 계획(사전 등록) [`label_agreement_v15_plan.md`](label_agreement_v15_plan.md) · 계산 판정표 [`label_agreement_v15.md`](label_agreement_v15.md) · 불일치 검토 기록 [`docs/dataset/review_log.md`](../docs/dataset/review_log.md) "v1.5 라벨 일치율 불일치 검토" · 참고 계산 [`data/label_agreement/reference_v15.json`](../data/label_agreement/reference_v15.json)

## 요약

- **질문** — 이 프로젝트의 정답 라벨은 검토자 한 명이 기준서를 만들고 그 기준서로 확정했다. 같은 기준서로 다른 QA가 판정해도 같은 답이 나오는가?
- **결과** — 나오지 않았다. 외부 게임 QA 2명이 63건을 블라인드로 판정한 결과, 6칸 모두 사전에 정한 기준에 못 미쳤고, Critical 문항을 Critical로 알아본 비율도 75%·55%로 기준(90%)보다 낮았다.
- **조치** — 어긋난 177건을 모델 응답을 보지 않은 채 하나씩 검토했다. 125건은 라벨이 맞고 채점자가 기준을 잘못 적용한 경우, 52건은 채점자의 답도 기준서로 설명되는 경우(허용 답 추가, 그중 2문항은 기존 라벨 자체가 틀림)였다. 기준서를 v1.5로 보완하고 v1.5 평가셋을 만들었다.
- **영향** — 모델 성적을 v1.5 라벨로 다시 세어도 v1.4에서 내린 판정(M2 채택, qwen2.5:7b 유지)은 바뀌지 않았다. 회귀 게이트는 v1.5 정답표로 옮겼다.

## 1. 왜 쟀나

모델이 몇 % 맞혔는지, Critical을 몇 건 놓쳤는지, 변경이 회귀인지 — 이 프로젝트의 모든 숫자는 **정답 라벨이 맞다는 전제** 위에 있다. 그런데 라벨은 검토자 한 명이 만든 기준서로 그 검토자가 확정했다. 기준서에 모호한 문구가 있어도 만든 사람 머릿속에서는 뜻이 분명하므로, 혼자서는 드러나지 않는다.

다음 단계인 확신도 기반 라우팅(확신하는 건은 자동 등록, 아닌 건은 사람 검토)은 "자동으로 처리한 건이 얼마나 맞는가"를 재야 한다. 정답표가 흔들리면 그 숫자도 흔들린다. 그래서 라우팅보다 라벨을 먼저 쟀다.

게임 QA 실무로 보면 **심각도 기준표를 새로 만든 뒤 다른 QA들에게 같은 이슈를 판정하게 해 맞춰 보는 교차 판정(캘리브레이션)** 이다. 사람마다 갈리는 항목이 나오면 기준표 문구가 모호하거나, 원래 부서마다 판단이 갈리는 영역이다.

## 2. 어떻게 쟀나

| 항목 | 내용 |
| :--- | :--- |
| 채점자 | 프로젝트에 참여하지 않은 게임 QA 2명. 채점자1은 시니어급 퍼블리셔 QA, 채점자2는 주니어급 개발 QA |
| 문항 | 개발용 63건 × 6칸(분류·우선순위·모듈·재현 정보·발생 빈도·처리). 최종 평가용 25건은 봉인 원칙에 따라 보내지 않았다 |
| 채점자가 본 것 | 모델이 받는 입력과 같은 리포트 원문, 판정 기준서(당시 v1.4)를 옮긴 채점자용 안내서 |
| 채점자가 보지 못한 것 | 정답 라벨, 판정 근거, 원래 문항 번호(A01·S01 등은 "까다로운 집중 세트"를 드러내므로 Q01~Q63으로 섞음), 모델 응답, 다른 채점자의 판정 |
| 판정 방식 | 엑셀 드롭다운. 선택지는 모델 출력 형식과 같아서, 사람 답을 모델 응답과 **같은 채점 함수**로 채점할 수 있다 |

**지표 두 가지**

- **허용 답 일치율** — 채점자 답이 정답 라벨의 허용 답 안에 든 비율. 모델 정답률과 같은 잣대다.
- **κ(카파)** — "우연히 맞을 확률"을 뺀 일치도. 예를 들어 63건 중 50건이 "결함"이면, 아무 생각 없이 전부 "결함"이라고 답해도 일치율이 79%가 나온다. κ는 이런 부풀림을 걷어 낸다. 0이면 우연 수준, 1이면 완전 일치이고, 0.61부터 "상당한 일치"로 본다(Landis·Koch, 1977).

판단 기준(사전 등록)은 판정을 받기 전에 커밋했다. 처리·분류·우선순위는 일치율 85% 이상과 κ 0.61 이상, 모듈·재현 정보·발생 빈도는 일치율 75% 이상, Critical 인식률은 90% 이상이다. 두 채점자 **모두** 넘어야 그 칸을 신뢰한다. 칸마다 엄격도를 다르게 둔 것은 "틀렸을 때 뒤 단계에서 바로잡을 수 있는가" 때문이다. 처리·분류·우선순위가 틀리면 이슈가 엉뚱한 곳으로 가거나 Critical이 묻히지만, 모듈·재현 정보·발생 빈도는 재배정·재현 단계에서 바로잡힌다.

## 3. 결과 — 6칸 모두 기준 미달

| 칸 | 기준 | 채점자1 일치율 / κ | 채점자2 일치율 / κ | 두 채점자끼리 κ |
| :--- | :--- | :---: | :---: | :---: |
| 처리 | 85%, κ 0.61 | 63.5% / 0.46 | 55.6% / 0.42 | 0.38 |
| 분류 | 85%, κ 0.61 | 77.8% / 0.56 | 66.7% / 0.44 | 0.47 |
| 우선순위 | 85%, κ 0.61 | 77.8% / 0.59 | 63.5% / 0.47 | 0.43 |
| 모듈 | 75% | 65.1% | 58.7% | 0.50 |
| 재현 정보 | 75% | **87.3%** | 73.0% | 0.44 |
| 발생 빈도 | 75% | 73.0% | 68.3% | 0.45 |

| Critical 인식률 | 채점자1 | 채점자2 | 기준 |
| :--- | :---: | :---: | :---: |
| Critical 측정 20문항 중 Critical로 본 문항 | 15 (75%) | 11 (55%) | 90% |

**읽는 법**

- 재현 정보에서 채점자1만 기준을 넘었고, 나머지는 모두 미달이다. 칸 단위 판정은 "두 채점자 모두"가 조건이라 신뢰로 판정된 칸은 없다.
- 가장 낮은 칸은 **처리**(어디로 보낼지)다. 두 채점자끼리의 κ도 0.38로 가장 낮다. 정답 라벨을 떠나, 같은 기준서를 본 두 QA끼리도 처리 결정이 가장 많이 갈렸다.
- 이번 두 사람에서는 시니어 채점자의 일치율이 모든 칸에서 주니어보다 높았다(모듈 κ는 주니어가 조금 높음). 채점자가 2명이라 경력 효과로 일반화하지는 않는다.

## 4. 어긋난 177건을 어떻게 다뤘나

한 채점자라도 허용 답 밖을 고른 (문항, 칸)이 177건이었다. 계획(§5)에 적은 절차대로 처리했다.

1. 문항마다 정답 라벨, 두 채점자의 답·확신도·메모, 관련 기준서 조항을 한 표에 모았다.
2. **모델 응답은 보지 않았다.** 모델 답을 알면 "모델이 맞히는 쪽"으로 라벨을 고치고 싶어지기 때문이다.
3. 비용이 큰 실수부터 검토했다: Critical 미인식 → 두 채점자 모두 정답 밖 → 한 명만 정답 밖.
4. (문항, 칸)마다 아래 판정을 내렸다. ④ 기준서 보완은 대개 ①과 함께 적용했다. 판정 방향은 검토자가 정했고, 같은 원칙을 다른 문항에 적용하는 분류는 Claude가 제안해 검토자 승인을 받았다.

| 판정 | 건수 | 뜻 |
| :--- | :--- | :--- |
| ① 라벨 유지 | 125건 | 기준서대로면 정답이 맞다. 채점자가 기준을 잘못 적용했다 |
| ② 허용 답 추가 | 52건 (33문항) | 채점자의 답도 기준서로 설명된다. 정답을 하나 더 인정한다 |
| ③ 라벨 변경 | 2문항 (B17, S08) | 기존 라벨이 틀렸다 (②에 포함) |
| ④ 기준서 보완 | 기준서 v1.5 | 규칙이 모호하거나 빠져 있었다. 대부분 ①과 함께 판정 |

**대표 사례**

| 문항 | 쟁점 | 판단 |
| :--- | :--- | :--- |
| B17 | 전화를 받고 돌아오면 화면이 멈춰 앱을 다시 켜야 함(5번 중 5번) | 두 채점자 모두 Critical로 봤다. 기존 라벨(Major)이 틀렸다. "버그로 앱 재실행이 반드시 필요한 현상이 반복되면 Critical" 규칙을 기준서에 추가 |
| S08 | 욕설 글자 사이에 숫자·점을 끼우면 필터를 통과 | 두 채점자 모두 개선 제안으로 봤다. 개발사 텍스트 오류(Critical 후보)가 아니라 필터 규칙 보강이 필요한 개선 제안으로 라벨 변경. 재채점 뒤 검토자가 다시 확인해도 개선 제안·Major·개발 배정이 맞다고 판단해 v1.5 라벨을 유지 |
| A04·B13·A10·A03 | 정보가 부족한 결함 제보를 "정보 요청 후 보류" 대신 "등록(재현 대기)"로 보냄 | 개발 QA가 재현을 시도하는 것도 합리적이다 → 허용 답 추가 |
| S10c·S15·S11 | 기기·상황이 적힌 유저 제보를 "재현 정보 부족"으로 봄 | 기준서(R-2)대로면 충분하다 → 라벨 유지 |
| 여러 문항 | 리포트에 없는 빈도("항상")를 추론 | 적힌 빈도만 옮긴다 → 라벨 유지, 기준서 F-1 문구 보완 |

## 5. 무엇이 바뀌었나

**기준서 v1.5** ([`docs/dataset/triage_guideline.md`](../docs/dataset/triage_guideline.md)) — 주요 변경:

- **앱 재실행 규칙** — 버그로 앱 재실행이 반드시 필요한 현상이 반복되면 Critical·긴급 사인 요청
- **필터 우회와 텍스트 오류 구분** — 개발사가 넣은 민감한 텍스트 오류만 Critical 후보(P-B2). 유저가 필터를 우회하는 것은 개선 제안
- **정보 부족 제보** — 개발 QA가 재현을 시도하도록 등록(재현 대기)로 보내는 것도 허용(H-3). 크래시처럼 Critical일 수 있는 현상은 등급을 추정해 등록하는 것도 허용(H-3a). 정보가 없을 때 판단보류가 원칙인 것은 그대로다
- **처리 출처 구분 표** — 내부 QA가 재현한 건은 개발 배정, 유저 제보는 등록(재현 대기)
- **결함이 아닌 글의 재현 정보(R-6)** — 판정 수집 중 두 채점자 모두 18곳을 비워 둔 데서 드러난 빈틈

**v1.5 평가셋** ([`data/eval_v15/aether_raid_v15.json`](../data/eval_v15/aether_raid_v15.json)) — 개발용 33문항 53칸의 허용 답이 바뀌었다. Critical 측정 문항은 20 → 17건(B17 추가, S04·S08·S09·B12 제외), 사람 검토 측정 문항은 11 → 10건. v1.4 평가셋 파일은 그대로 두고 새 파일로 만들었다. 최종 평가용 25건은 이미 쓴 세트라 바꾸지 않았다(아래 §9 F08).

## 6. 모델 성적에 준 영향

모델을 다시 돌리지 않고, 저장된 v1.4 실행 기록을 v1.5 라벨로 다시 채점했다([`rescore_v15.md`](rescore_v15.md)). 응답은 그대로이고 정답표만 바뀌었으므로, 숫자 차이는 모두 라벨에서 나온다.

| 채택 구성 (qwen2.5:7b + M2, 개발용 378응답) | v1.4 라벨 | v1.5 라벨 |
| :--- | :---: | :---: |
| 처리 정답률 | 68.8% | 73.3% |
| 전 칸 정답 | 19.8% | 20.9% |
| Critical 누락 / 측정 응답 | 17 / 120 (14.2%) | 14 / 102 (13.7%) |

- Critical 누락은 건수가 줄었지만 비율은 거의 같다. S04가 측정 문항에서 빠지며 누락 5건이 사라졌고, 새로 Critical이 된 B17에서 2건을 놓쳤다.
- v1.4의 방법 비교(M2 채택)와 모델 비교(qwen2.5:7b 유지)를 v1.5 라벨로 다시 계산해도 판정은 같았다(참고 재판정).
- gemma4:12b는 v1.4 라벨에서 Critical 누락 0건이었지만 v1.5 라벨에서는 6건(모두 B17)이다. "gemma는 Critical을 놓치지 않는다"는 v1.4의 관찰은 v1.5 기준에서는 성립하지 않는다.
- 회귀 게이트를 v1.5 정답표로 옮겼다([`regression_gate_v15.md`](regression_gate_v15.md)). 기준 값은 그대로이고, 같은 구성은 PASS, 체크리스트를 뺀 구성은 Critical 누락 증가로 FAIL을 냈다.

## 7. 두 채점자끼리 갈린 문항 — 라우팅의 사람 검토 근거

계획 §5는 두 채점자끼리도 갈린 문항을 "새 경계 사례 후보"로 기록해 라우팅의 사람 검토 근거로 쓰기로 했다. 정답 라벨과 무관하게 두 채점자의 답만 비교했다(모듈은 고른 모듈의 집합으로 비교).

| 칸 | 처리 | 우선순위 | 분류 | 모듈 | 발생 빈도 | 재현 정보 |
| :--- | :---: | :---: | :---: | :---: | :---: | :---: |
| 두 채점자 답이 다른 문항 (63건 중) | 32 | 29 | 21 | 39 | 26 | 18 |

63건 중 55건에서 한 칸 이상이 갈렸고, 비용이 큰 칸(분류·우선순위·처리)이 갈린 문항도 43건이다. **이대로는 "사람이 봐야 할 문항"을 골라내는 신호가 되지 못한다.** 대부분이 한 채점자의 기준 적용 실수이기 때문이다. 그래서 갈린 비용 큰 칸을 v1.5 허용 답으로 다시 나눴다.

- **두 답이 모두 v1.5 허용 답 안** — 기준서로 봐도 둘 다 맞는, **원래 갈리는 판단**이다. 14문항.
- **적어도 한쪽이 허용 답 밖** — 기준서대로면 적어도 한쪽이 틀린 **기준 적용 차이**다. 처리 25, 우선순위 20, 분류 20(문항·칸 기준, 겹침 포함). 두 답이 모두 허용 답 밖인 경우도 10칸 있다(B20 등).

v1.5 허용 답은 불일치 검토에서 바로 이 채점자 답들을 보고 넓혔다. 따라서 이 나눔은 검토자의 판단을 다시 보여 줄 뿐 독립된 근거가 아니며, 라우팅 설계의 출발점으로만 쓴다.

**원래 갈리는 판단 14문항**은 세 묶음이다.

| 묶음 | 문항 | 두 채점자의 답 |
| :--- | :--- | :--- |
| 낮은 등급의 경계 | B11·B10·B08·B06·S05 | Minor ↔ Trivial |
| 정보 부족 제보의 처리 | A04·B13·A10·A03 | 정보 요청 후 보류 ↔ 등록(재현 대기) (A03은 판단보류 ↔ Major도) |
| 경계 규칙·특수 상황 | B12(특정 기기 확정 크래시, P-B3), S07(얼굴 변형 조롱, P-B1), S10b(기간 만료 수치 문의, P-B6), S19(보상 불만), B14(폴드 화면 잘림) | B12 우선순위 Major ↔ Critical·처리 등록(재현 대기) ↔ 긴급 사인 요청, S07 우선순위 Major ↔ Minor, S10b 분류 버그 아님 ↔ 문의·건의·우선순위 해당 없음 ↔ 판단보류, S19 처리 폐기 ↔ CS 응대, B14 처리 개발 배정 ↔ 등록(재현 대기) |

**라우팅에 주는 시사점**

- 첫 두 묶음에서 갈린 칸(Minor ↔ Trivial, 정보 요청 후 보류 ↔ 등록(재현 대기))은 어느 쪽으로 가도 긴급 경로를 타지 않고, 정보 부족 제보는 어느 쪽이든 사람(작성자 또는 개발 QA)이 다음 정보를 얻는다. 다만 이는 **그 칸의 갈림**에 대한 해석이다. 9문항 중 6문항(A04·B13·A10·A03·B08·S05)은 다른 비용 큰 칸에서 기준 적용 차이가 함께 있었고, 비용 큰 칸 전체가 허용 답 안에서만 갈린 문항은 B11·B10·B06 셋뿐이다. "이런 칸은 모델이 어느 쪽을 골라도 자동 처리해도 된다"는 것은 라우팅 단계에서 측정할 가설로 둔다.
- 셋째 묶음, 특히 **B12처럼 Critical 여부가 갈리는 문항**은 사람 검토로 보낼 후보다. 셋째 묶음 5문항 중 3문항(B12·S07·S10b)이 경계 규칙(P-B1~B6) 문항이다. 경계 규칙 문항인 S05(P-B5)는 Minor ↔ Trivial이라 첫 묶음에 있다.
- 기준 적용 차이가 큰 칸(처리)은 "사람도 자주 틀리는 판단"이다. 모델이 이 칸에서 낮은 확신도를 보이면 검토 큐로 보내는 근거가 된다. 확신도 신호와 실제 오류의 관계는 라우팅 단계에서 따로 측정한다.

## 8. 참고 — v1.5 라벨로 다시 계산한 채점자 일치율

**이 값은 독립된 측정이 아니다.** 불일치 검토에서 채점자 답을 보고 허용 답을 넓혔으므로, 다시 계산하면 오르는 것이 당연하다. 사전 등록 판정(6칸 모두 검토, Critical 인식률 미달)을 대신하지 않으며, 기준을 넘었는지 판정하지도 않는다. "검토로 무엇이 얼마나 정리되었나"를 보여 주는 참고로만 적는다.

| 칸 | 채점자1 v1.4 → v1.5 | 채점자2 v1.4 → v1.5 |
| :--- | :---: | :---: |
| 처리 | 63.5 → 74.6% | 55.6 → 66.7% |
| 분류 | 77.8 → 81.0% | 66.7 → 71.4% |
| 우선순위 | 77.8 → 90.5% | 63.5 → 74.6% |
| 모듈 | 65.1 → 92.1% | 58.7 → 81.0% |
| 재현 정보 | 87.3% (같음) | 73.0% (같음) |
| 발생 빈도 | 73.0% (같음) | 68.3% (같음) |
| Critical 인식 | 15/20 → 16/17 | 11/20 → 11/17 |

- 모듈이 가장 많이 올랐다. 모듈은 "가까운 다른 모듈"을 문항별로 허용한 경우가 많았다.
- 재현 정보·발생 빈도는 그대로다. 이 두 칸은 대부분 라벨을 유지하고 기준서 문구만 보완했다. 채점자의 판정이 틀렸다는 판단이므로 일치율이 오르지 않는다.
- v1.5 라벨에서도 두 채점자 모두 놓친 Critical 문항은 **B20**(내부 QA가 "건의"로 올린 분쟁 지역 명칭 오기)이다. 작성자가 건의로 올려도 내용으로 판단한다는 규칙을 기준서에 보완했지만, 라벨은 바꾸지 않았다. 채점자2는 서버 장애(S16)·데이터 소실(S11)·진행 차단(B02) 같은 Critical 문항도 놓쳤다. 채점자 한 명의 결과라 경력과의 관계로 일반화할 수는 없지만, 기준서를 읽는 것만으로는 Critical 판단이 맞춰지지 않는다는 점은 분명하다.

## 9. 한계

- **채점자가 2명이다.** κ는 표본이 작으면 오차가 크다. 수치보다 어느 문항에서 갈렸는지를 주로 봤다.
- **경계 규칙의 판정이 기준서에 들어 있다.** 경계 문항의 일치율은 "원래 판단이 갈리는가"보다 "그 규칙에 해당하는 상황임을 알아보는가"를 잰다.
- **검토는 검토자 한 명이 했다.** 채점자 답을 보고 라벨을 넓혔으므로, 다음 측정에서 새 라벨이 다른 QA에게도 통하는지는 아직 모른다. 새 v1.5 최종 평가용 세트를 만들 때 다시 확인할 대상이다.
- **최종 평가용 F08** — 로비 화면 멈춤·앱 재실행 필요·누를 때마다 발생하는 문항으로, v1.5 앱 재실행 규칙으로는 Critical이지만 v1.4 라벨(Major)을 그대로 두었다. 이미 사용한 세트라 고치지 않았으며, v1.4 최종 평가 결과를 인용할 때 이 차이를 함께 적는다.
